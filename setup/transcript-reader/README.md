# Transcript reader

Reads Firstmate Claude Code, Codex and GitHub Copilot CLI session logs back as a conversation, and lets you answer a reply in its own Herdr pane (Claude and Codex panes, a Claude under any config folder included; a Copilot session is read only).
Design and decisions: `DESIGN.md`.

## Run it

```bash
python3 setup/transcript-reader/reader.py add <session id, 8-char prefix, or Herdr pane label>
python3 setup/transcript-reader/reader.py          # rebuild every listed session, start the server, print the links
```

`reader.py` also has `remove`, `list` and `panes` (live Herdr panes to pick from), and `adopt` (what Sync runs to list the live panes the list lacks).
The reader has its own server, in its own process, apart from `setup/serve.sh` and the pages that one serves. `reader.py` starts it when needed, on port **8768** (8765 and 8766 belong to other pages). For another port, set `PMOS_READER_PORT`, which `reader.py` and `serve.sh` both read. `serve.sh --port` changes only that one command: `reader.py` still looks on 8768 and starts its own server there.
`reader.py` checks which copy of the repo answers on the port and says so, with where that other copy runs (`Port 8768 serves another copy of the repo (/path)`).
Start and stop it by hand with `bash setup/transcript-reader/serve.sh [start|stop|restart|status|passcode|cert] [--port <port>] [--tailnet] [--tailnet-https]` (the rest are for the phone, below). `stop` only stops this copy's own reader server, never another copy's or another app's.
After changing `api.js`, `server.js` or `worker.js`, restart it: `bash setup/transcript-reader/serve.sh restart`. **A server started before the quick-reply change (see "Speed from a log write to the page") needs one restart to get it**: until then it rebuilds the old way, on the page's poll, and an open page learns of a build on its next 2-second tick. `reader.py` and the page code need no restart: the server runs the `reader.py` it finds when it starts its worker (a restart, or ten minutes idle), and that worker starts itself again from the new files when `reader.py` or the builders change.

**A restart keeps the switches.** A start or restart of the reader through `serve.sh` remembers what it started with, in `out/serve-settings-<port>.conf` (owner-only, gitignored with the rest of `out/`, one file per port so a lab reader on a spare port never inherits or changes the live one's; `PMOS_READER_SETTINGS_FILE` names another file). A later `start` or `restart` with no flags, by anyone and also the one `reader.py` does, comes back with the same switches. Kept: `--tailnet`, `--tailnet-https` and `--https-port`, and the switches `PMOS_READER_BOARD`, `_BOARD_SEND`, `_BOARD_MARKS`, `_BOARD_ANSWER`, `_BOARD_REVIEW`, `_BOARD_TAILNET`, `_FLEET_TIMELINE` and `_STORE_RECORDER` (a path; one that no longer exists is left off with a note). Not kept: folders, caches and the passcode file. Order, highest first: a flag, a set environment variable, the kept file, off. An explicit off: `--no-tailnet`, `--no-tailnet-https`, or the variable set to `0` (`PMOS_READER_BOARD_SEND=0 serve.sh restart`; the recorder takes `off`). `--fresh` ignores the kept file for that start, and that start is then what is kept. A reader started before this existed (no file) is taken over by its first `restart`: it keeps the switches and addresses the running reader has. `serve.sh status` shows the switches on in the running reader (read from the process), the settings kept for the next start, and says when they differ. Tests: `node --test setup/transcript-reader/servesettings.test.js` (real servers on spare ports; a start, a plain restart, an explicit off, `--fresh`, the tailnet request, the recorder, a hand-started reader, a file with odd lines).

Open the printed `http://localhost:8768/setup/transcript-reader/out/prototype.html` link in one of the supported browsers:

- **Chrome** (checked in Chrome 155 at `http://localhost:8768`): the page, the live badge, Send disabled and enabled (empty box, a working, idle or Done agent, an agent at a permission prompt or in an unknown state, a closed pane), a single message and a batch sent to the right pane, the Documents tab and a message about a file, and phone width (390 px) all work.
- **VS Code Integrated Browser**, the browser tab in VS Code's editor area.

Not supported: the **VS Code Simple Browser**. It shows a page inside a frame, and the page refuses to be framed on purpose (`frame-ancestors 'none'`, `X-Frame-Options: DENY`), so that no other page can embed it. Use the Integrated Browser or Chrome instead. Safari and Firefox were not tried.

Opened in a supported browser, the page:

- **Refreshes itself.** While a page is open, the server watches the logs of the listed sessions and, when one writes a new turn, rebuilds the pages at once (the first write after a quiet spell at once; while logs keep changing, one rebuild at most every 2 seconds for all the writes since the last, and nothing at all while no page is open); the page is told the moment the build is there and swaps in the new turns where you are reading. A reply shows about a second and a half after the agent wrote it ("Speed from a log write to the page", below). When the page's own code changes it reloads, keeping the replies you expanded and your place.
- **Syncs on demand.** The line under the title says when the page last heard from the server ("Synced 09:02:14", changing with every 2-second poll, and "Not syncing since ..." with an "offline" badge once the server stops answering). **Sync** reads Herdr again and rebuilds from the session logs and the fleet records now, then swaps in the whole build: the session list, each session's live or ended state and the newest turns of every listed session, so any session you switch to afterwards is current, while the conversation you are reading keeps its place. Sync also lists every live Herdr pane running Claude or Codex whose session is not on the reading list yet (a `/clear` joins and a label reads as for Follow Herdr), and brings all of them up to date in the same click. A session you took off the list (the page's Close, `reader.py close` or `remove`) stays off until you add, reopen or follow it again, and the default Herdr session is never read. It sends nothing to any pane. It only reads; it writes `out/` like any rebuild. A server started before Sync existed says so and the page reads what it can.

### Codex crew panes

The local reader discovers native Codex CLI rollouts under `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`.
It maps a Herdr Codex pane to the root rollout whose `session_meta` has `source: "cli"` and the same foreground working directory.
Subagent rollouts are excluded because their source is not `cli`.
Only the first line of each rollout is read, and it is remembered by file path, mtime and size, so listing a large `~/.codex/sessions` does not read the conversations.
The parser reads user and assistant messages, Codex tool calls and results, and plaintext reasoning summaries.
It ignores encrypted reasoning content and duplicate `event_msg` records.
Send checks that the exact Codex rollout still owns the pane's foreground before it clears the input and prompts it.
A leading `$` waits 1.2 seconds before submission so Codex skill autocomplete can settle.
This rollout covers local pane discovery and Send; hosted and phone behavior remains unchanged.

### Copilot panes (read only)

A Herdr pane that runs GitHub's Copilot CLI (`agent: copilot`) shows up like a Claude or Codex one, and its conversation reads the same way, live as the session goes on.
The reader reads `~/.copilot/session-state/<session id>/events.jsonl`: your messages (what you typed, not the text the model was given), Copilot's replies, its tool steps (shell commands, file views, searches, patches with their diffs, questions asked, helper agents) and the working notes it wrote before a step.
Encrypted reasoning, the system prompt and a helper agent's own turns are never read.
Which session a pane shows comes from the pane's `copilot` process: its own log registers the session at each start, `/resume` and `/new`, and the reader keeps the newest one it saw in `out/copilot-panes.json` because that log is rotated at 10 MB. A pane whose session cannot be told is left unmapped, never guessed.
`reader.py add <id, 8-character prefix or events.jsonl path>` and Sync's listing of live panes take a Copilot session like any other.
**Send is off.** The message bar says "Sending to Copilot is not supported yet. Copy still works.", and the server refuses with the same words before it asks Herdr anything, so no key or text can reach a Copilot pane.
The hosted and phone copies take a listed Copilot session as they take any other, with Send off there too; `sync.py`'s default scope still lists Claude logs only.
Details and the limits: `DESIGN.md`, "Copilot CLI panes, read only".

### Claude under another config folder

A Claude Code run with another `CLAUDE_CONFIG_DIR` (a second account, for example `~/.claude-personal`) keeps its logs and process records in that folder, not in `~/.claude`, and Herdr's Claude hook is set up in `~/.claude/settings.json` only, so Herdr names no session for such a pane.
The reader looks in every folder named `~/.claude<anything>` that holds a `projects/` or `sessions/` folder (a file such as `~/.claude.json`, or another tool's `~/.claude-xyz` folder, has neither), in the folder `CLAUDE_CONFIG_DIR` names for the reader's own process, and in each folder of `PMOS_READER_CLAUDE_HOMES` (absolute paths, separated like `PATH`), for a place outside the home folder.
No account's name is written anywhere: a new account is found at the next look, with no restart.
Such a pane is mapped to its session the way every Claude pane is, through its foreground process and that process's record in `<config folder>/sessions/<pid>.json`, so it lists, reads, follows (Follow adds it as it does any focused pane), stays live (the server watches its log) and is sent to under the usual Claude checks.
A test or a lab that names the projects and sessions folders itself (`PMOS_READER_PROJECTS`, `create({ projectsDir, claudeSessionsDir })`) reads those alone.
Details: `DESIGN.md`, "Claude under another config folder".
- **Pins messages.** **Pin** on a message or a reply keeps it; **Pins · n** in the controls lists this conversation's pins or all of them, and a click goes to the message (opening the wake-up run that hides it, in place: a conversation already on screen is not drawn again). A pin names the message by its turn's id from the session log, so it holds across rebuilds and `/clear`. Each pin can carry an optional owner-written description, editable from its row; without one, the list uses the first meaningful line of the message or reply. Pins are kept in `~/.config/pmos-transcript-reader/pins.json` (`PMOS_READER_PINS` moves it), outside the repo, owner-only (folder 0700, file 0600), holding no message text. A page that cannot reach the server (a file copy, a server that predates pins) keeps them in this browser, and moves them into the file once it can. The hosted copy keeps them in the browser, per viewer.
- **Hides messages and replies.** **Hide** beside Pin on a message or a reply takes it out of this view, for what is not worth reading again; a toast right after offers **Undo**. It is a view setting only: the agent's session log is never opened for writing, and nothing in the conversation's text changes. **Hidden · n** in the controls (an eye icon in the folded header, shown only while the conversation has hidden messages) shows the hidden ones in place, dimmed, each with **Show again**, and puts them away again when pressed again. A hide names the message by its turn's id and part, like a pin, so it holds across rebuilds and `/clear`; the server keeps the set in `~/.config/pmos-transcript-reader/hidden.json` (`PMOS_READER_HIDDEN` moves it), outside the repo, owner-only, holding no message text, so the laptop and the phone agree (the state poll carries its revision). A page that cannot reach the server (the hosted copy, a file copy) keeps them in this browser. "Next ask" and "Your next" skip a hidden part; the "need you" count in the summary still counts an ask whose reply is hidden, because hiding does not answer it.
- **One row for a pane.** A pane that was cleared many times is one conversation, under its newest session, reading back through every session of the pane the reading list holds (up to 40, each marked by a divider); an older session listed on its own (reopened by hand, starred) does not stand as a second row. A session's "closed pane" tag says that no pane runs it now; a session a pane runs has none, whether or not it was reopened by hand once.
- **Builds a new Herdr tab on a pick.** The session picker has a group, **Herdr tabs not on the reader · n**, of the live panes (Claude, Codex, Copilot) whose session has a log and is not on the reading list. Choosing one lists it and builds the page with it at once (a quick rebuild: it leaves the sweep for closed panes to the next ordinary one), then opens it: well under a second on a warm server, against the several seconds Follow Herdr took, and it needs no focus. The rebuild worker is kept running while a page has been open in the last hour, so a pick after a quiet spell is not a cold start.
- **Stars sessions.** The star beside the session picker (in the folded header and in the controls) stars or unstars the session on screen; starred sessions sit in a **Starred** group at the top of the picker, each marked with a star, ahead of the running sessions and Closed panes, **newest star first** (a session starred now goes to the top; unstarring it and starring it again puts it back on top). A star names the conversation, so it holds across rebuilds, Sync and `/clear`. Stars are kept like pins, in `~/.config/pmos-transcript-reader/stars.json` (`PMOS_READER_STARS` moves it), outside the repo and owner-only, holding no text, written newest first (a file from before, oldest first, is put in that order when the server starts; the hosted copy's stars are newest first too), or in this browser when the server cannot be reached (the hosted copy, always).
- **Marks a reply's answer sheet as wrong or missing.** A reply with an answer sheet (or one that asks something of you, or reads like a keyed-answer reply: `R1=`, "Reply with/like") has a **Sheet** button after Reply, on the served page. It opens a panel that says what the reply has now (a sheet with N questions, or none) and offers **Mark: this sheet is wrong** (or **Mark: this should be a sheet**, when it has none), **Clear mark** and **Re-render**. Re-render builds every page again now (the worker starts again from the code on disk) and says what the reply is now: "Drawn again: it is an answer sheet with 9 questions" or "still no answer sheet". A mark names the reply by its turn id and holds no text: it is kept in `~/.config/pmos-transcript-reader/sheet-flags.json` (`PMOS_READER_SHEET_FLAGS` moves it), outside the repo and owner-only. `python3 setup/transcript-reader/reader.py sheet-flags` lists the marked replies and what the finder makes of each today; `sheet-flags --shape <turn id>` prints one reply's shape with its words masked (table pipes and headings, keys, lettered choices and "Reply like" stay). To keep a case as a parser test, fill that shape with invented words (never the private reply) into `answer-sheet-fixtures/<name>.md` and write `<name>.expect.json` beside it; `test_questionnaire.py` (`FlaggedFixturesTest`) runs every pair. The 2026-11-04 case (a `Key | Call | Recommended` table with the choices inside the Call cell) is the first one: the finder now reads a Key column, takes a Call cell as the question with `a` ...; `b` ... choices (and their words), and "Reply like" as the reply line.
- **One sheet is one review group.** The keys the reply line asks for (`Reply with keyed answers: X1=...; X2=...`) name the group by their letters, so a keyed table row of another group that the reply only mentions (a recap of earlier calls, in a table that looks like cards) is not a card on the sheet; the sheet says in its margin, "Not on this sheet", which keys it left out. A table that names keys and asks nothing (`Key | In plain words`, a status list) is never a table of cards, and a section of the reply that holds only such a recap is not in the sheet's "What this is about" text. A reply line that names only some of a group's keys (an example) keeps every card of those letters, and one whose letters match no card keeps them all. Lettered choices separated by ` / ` lose the slash. A reply flagged as wrong keeps its shape as a fixture in `answer-sheet-fixtures/` (invented text), where `test_questionnaire.py` holds the parser to it.
- **Reads choices out of a table cell, and knows review groups.** A table whose Answer cell holds its choices as backtick letters with their words (`` `a` agents only / `b` agents plus the whole Mac ``) gives each letter its words, in the reply's order, and a Recommended cell that only names the letter (`` `b` ``) marks that choice with a star and shows it by its words. A reply written in two or more `## Review group A - title` headings that each hold cards is still one sheet (one answer line covers all its keys), but each group stands under its own heading and lead-in above its own cards, and the text above the sheet no longer carries the first group's heading. One group heading, or none, is one sheet as before.
- **The answer sheet lists the open conversation's sheets only.** The title bar's "Answer sheet" link carries the conversation on screen (`questionnaire.html#s=<session 8>`; the hosted copy's `sheet.html#s=...`), as a reply's own link already did (`#q=<session 8>:<time>`), and the sheet's picker lists only that conversation's sheets (a questionnaire from before a `/clear` counts as the same conversation). The sheet's "← Reader" returns to that conversation. A conversation with no sheet says so instead of showing another's. A sheet page opened with no address (a bookmark of it) still lists every conversation's, and a pick made there is kept as `#pick=`, which does not narrow the list when the page reloads.
- **A page that opens names its pane at once.** The dock cannot name the pane a message goes to until the server's first `/state` answer comes, and that answer waits for a fresh Herdr read (half a second or more). A page's first call (`/state?boot=1`) is therefore answered from the server's last Herdr reading when that is under 10 seconds old, while the server takes a fresh one; the page's next poll, two seconds on, brings it. Every later call, `Sync` and every Send read fresh. This is what makes the way back from the answer sheet (a new page, which cannot be kept by the browser: the pages are sent `no-store`, and the full page is about 12 MB) ready in about the time of its first paint. Measured by `e2e/sheet-back-latency.js`.
- **Opens the reply a sheet was made from, beside the sheet.** Each sheet keeps the full text of the reply it was read from (so it is there offline and in the hosted copy too), and an **Original reply** button under the sheet's title opens it in a panel drawn by the reader's own markdown code: tables with their header row, code boxes with Copy, lists, links and headings, as in the conversation. In a window 900 px wide or more the sheet moves to the left and the panel takes the rest, so the two are read at once; on a narrower one the panel floats above the answer line (Close, the same button or Esc gives the sheet back; Close is a 44 px control on touch widths). A wide table scrolls inside the panel. The panel stays open for the tab, so the next sheet opens beside its reply too. Checked in headless Chrome by `e2e/sheet-reply-check.js`.
- **A session the reader does not list opens as itself.** A page opened on `#s=<session>` for a session that is not on the list (no transcript yet, or a pane closed here), and an address like that followed in the open page, show **No transcript yet for this session** with the session's id, in the picker too, and no message box, so nothing can go to another pane. They never show another conversation, which is what they did before (the list's first on a fresh load, the open one when followed). The page opens the session in place when a build lists it (the address may be the id's first 8 characters). Picking another conversation, or a listed address, leaves it. The same goes for a live Herdr tab picked in the picker whose agent has written no transcript yet. A conversation this tab merely read last, found with no address, going missing still opens the list's first, with the notice. Checked on the full page and the lite page by `e2e/session-unlisted-check.js`.
- **Follows Herdr.** With "Follow Herdr" on, the reader shows the session of the pane Herdr has focused. A session not on the reading list is added. While you write in the message bar, the switch waits until you send or leave the box, and the bar says where Herdr is. The session the page opens on wins over the first focus when the address names it (`#s=…`, which the page keeps up to date) or when this tab read it last (a reload, or the answer sheet's "← Reader").
- **Keeps an open session list steady.** The session picker is one element kept as the page draws itself again, and it is changed only when what it would show differs and never while its list is open: a build that lands while you browse (every second or two while agents write) leaves the list as it is, keeping its place and anything you typed to jump to a name, and a new session or a changed state shows once the list closes. (A browser without `:open` counts a picker with the focus as open.) Each option holds the session's id, not its place in the list (every build puts the list in a new order, newest reply first), so a choice made from a list drawn before the last build still opens the session it names, with that session's message box.
- **Keeps live panes only.** When a listed session's Herdr pane closes, the server rebuilds the page and `reader.py` drops that session from the reading list. A session cleared with `/clear` stays while its pane runs the newer session, and the newer session is listed as soon as it has a log, even when the pane already runs it a few seconds before the log exists (the first message after a clear writes it): the server notices that a listed conversation's pane moved on to a session that is not listed, and lists it (`reader.py adopt`) on the first look after its log appears, with no other log needing to change. Until that log exists the conversation is not dropped for it. Only a conversation you read continues this way, never one you closed or removed. On a lab with a fake Herdr the page shows the cleared session running again 2 to 5 seconds after it can be read. A session is dropped when Herdr no longer lists its pane (within one life of a Herdr session the id of a closed pane is never reused; a session deleted and made again under the same name counts as new panes), when its pane now runs a different session that is not a later part of the same conversation, and when its pane runs no agent and has done so for over 15 minutes since that Herdr session's server started. Within those 15 minutes a pane whose agent has not come back yet (Herdr restarts bring panes back before their agents) keeps its session. A dropped session that runs in a pane again within two weeks of its last turn is listed again, unless you removed or closed it yourself. A session never seen in a Herdr pane (added by id or log path) stays, and nothing is dropped while Herdr shows no pane at all or one of its sessions cannot be read. An empty list is no failure: when the last listed pane closes, the page keeps that conversation on screen as a closed pane, and once none is shown it says so, with Closed panes in the picker. Close takes a conversation off the page too, on to the next one, and a reload does not list it again.
- **Keeps the conversation you are reading when its pane closes.** The page does not move to another conversation or aim the message bar at another pane. It stays on the same turn as a closed pane, with a note saying so and Send off, and the box keeps what you typed. "Keep it on the reader" lists it again until you press Close; picking another session instead takes it off the reader, and it stays under "Closed panes". A reload (new page code, a restarted server) or the conversation's address lists it again the same way and returns to the same place, with no message bar until it is back. An address naming a session the reader can no longer open says so above the conversation shown instead.
- **Titles the browser tab.** The tab reads `<picker name> · Reader` (`· Documents` in the document view, `Fleet timeline · Reader` on the timeline, "Transcript reader" with no conversation open), so tabs of several conversations tell apart; it follows a switch, Follow Herdr, Sync and a label change, in the hosted copy too.
- **Shows what each session is doing.** With the server running, each session in the picker shows its agent's state from Herdr and then its Herdr tab or pane label. A session whose pane was seen but no longer runs it (its agent exited and left the pane at a shell, or the pane closed) reads "closed pane" there and in the header, within one poll. Herdr can keep the id of an agent that has exited, so a pane that names no agent but keeps a session id is checked against what runs in its foreground, as a Claude pane is (plus the session's title only when two listed sessions share a label). The states are: Working, Waiting for you (a permission prompt or question), Done, Idle. The states follow Herdr while the page is open. A session with no running pane shows none. Herdr keeps a finished session Done until you visit its pane there, and it has no way to be told you read it elsewhere, so a Done session you have read here up to its newest turn shows Idle (in the picker and the message bar). That is kept in this browser only and leaves Herdr's own sidebar unchanged; a newer turn makes it Done again.
- **Reopens a closed pane to read.** The session picker lists the sessions an agent runs now, each by its Herdr label alone (a session's title is added only to tell apart two running sessions with the same label, never because a closed one has it). Under "Closed panes" it lists first the sessions still on the reading list that no pane runs (kept after the pane closed, reopened by hand, or never seen in a pane), then the sessions of panes closed in the last two weeks (one entry per conversation). Picking one adds it back, with its documents, and keeps it while its pane stays closed. "Close" takes it off again, and it returns to "Closed panes". From the command line: `reader.py reopen <full id>` and `reader.py close <full id>`; `reader.py add` of a closed pane's session does the same as `reopen`, and says so.
- **Chats with the session.** A message bar sits at the bottom of the Conversation and Documents views and writes to the session on screen (Enter sends, Shift+Enter starts a new line; on a phone, the Send button sends). For several comments at once, "Add" (Cmd+Enter or Ctrl+Enter) puts each one into a batch kept for that session in the tab, and Send then sends them all as one numbered message, with what is in the box last. Commenting on a new passage while a pointed comment sits in the box adds that comment to the batch first. Each batched comment has Edit (back into the box, keeping its place, so Send or Add puts it back where it was) and remove; **Clear all** in the batch's heading removes the whole batch with a second press: the first turns it into a red "Remove all 3?" with **Keep** beside it, and a question nobody answers is withdrawn after 6 seconds (the page asks for itself because a browser that shows no native dialog, such as VS Code's Integrated Browser, answers `confirm()` "no" and the button did nothing; the question is about that conversation's batch as it stood, so a comment added or another session opened asks again). A `/` command cannot join a batch. "Exact text" (one click) shows the whole message a batch sends, numbering and every pointer in full, and while the batch is not empty a one-line note in the bar says so ("3 comments - Exact text shows what Send types"). "Sends exactly" folds a long pointer (a reply the session no longer holds adds a log path) to one line that opens on a tap, so your own words stay in view. The batch list starts folded on every screen, on load and when you switch sessions, with its heading showing the count; click or tap the heading to open it. Add does not open it, and a list you opened stays open until you close it. A send removes only what it sent: anything written or added while it runs stays. It sends only when Herdr says the agent is idle, working or done, and the pane's foreground process is the named harness running that session (not a shell it was suspended to). "Reply" on a reply, or "Comment on this" after selecting a passage in it (or Cmd+Enter, Ctrl+Enter off the Mac, while the passage is selected and the cursor is not in a text box; the button shows the key on a screen with a keyboard), attaches a pointer to the bar, shown under "Sends exactly". A sent message shows at once, faded, until the session's log has a message of yours with the same opening words. A plain message takes you to the end of the conversation; a reply to an older turn keeps your place. `/clear`, `/exit`, `/quit`, `/compact`, `/logout` and `/rewind` ask first. The draft keeps its pointer and, during Edit, its place, across a reload or a switch to another session; after a `/clear` in the pane, the draft and batch move to the pane's newest session, and a pointer written before the clear says so. The pointer names the reply instead of copying it, for example `Re your reply at 10:57 ("Checkpoint for group A"): A2=link-only`. When the session no longer holds the reply (the pane cleared it since, or it came before the session's last compaction), the message also names the log and gives what the reply asked, or else its first few hundred characters. The answer sheet's Send does the same with the picked answers.
- **Slash commands and skills go as typed.** `/bearings`, `/bearings plain` or any other command or skill reference is sent exactly as written, alone (no pointer, no batch, no photos), through the same Send, Undo window and checks as a plain message, in the conversation's message bar and in the Tasks card's message box. Six commands that end or reset the session on the other end (`/clear`, `/exit`, `/quit`, `/compact`, `/logout`, `/rewind`) ask first, in the page: the first press of Send (or Enter) turns Send into **Confirm /clear** and Add into **Keep**, with the question in the line under the box ("Send /clear to alpha? It starts that session over. Press Confirm, or Keep to leave it."); Confirm goes on to the 5-second Undo window, and Keep, Esc, other words, another conversation or 6 seconds with no answer withdraws the question. The question is never a native `confirm()`: Conn's web view and the Integrated Browser of VS Code answer that "no" at once, which left `/clear` with a Send that did nothing. Only the command's own word counts (`/clear now` asks, `/clear-all` and `/clearly` do not).
- **Empties the pane's input box before sending.** Text typed in the Herdr pane and not sent would otherwise join the front of the message, so each send first deletes it (Ctrl+K and Ctrl+U, up to about 100 screen lines). These keys never stop a working agent, unlike Ctrl+C or Esc. Anything you had typed there is gone, so send from the pane itself if you want to keep it.
- **Undo a send.** Send does not send at once. It holds the message in the page for 5 seconds (the box locks, the Send button turns into "Undo 5", and the conversation shows the faded message as "Sending in 4 s · nothing has left this page yet" with **Undo** and **Send now**). Undo, or Esc, puts everything back as it was: nothing was asked of the server, the queue or any pane, so it says "Undone: it was never sent". After the window the message moves on and the faded message says where it is, and whether Undo is still possible:

  | Where the message is | Undo? | What the faded message says |
  |---|---|---|
  | In the 5-second window | yes | "Sending in 4 s · nothing has left this page yet" |
  | Held on the phone (laptop not reachable) | yes, once the laptop confirms | "Held on this phone since 14:05 …" with Undo; after Undo, "Undoing · waiting for the laptop to confirm it did not send this" until the laptop answers |
  | Queued for the laptop's next sync | yes, at once | "Queued 14:05 · waiting for the laptop to send it to alpha" with Undo |
  | The laptop is sending it, or has sent it | no | "… the laptop is sending it now · too late to undo" / "Sent by the laptop at 14:06 · waiting for alpha · too late to undo here" |
  | Sent straight to the pane (the Mac's own page) | no | "Sent 14:05 · waiting for alpha · too late to undo here" |
  | Sent while the agent was working | not from the reader | the same, plus "alpha was working, so Claude Code may hold this as a queued message until its turn ends. Press ↑ in the pane to take it back." |
  | Refused (the laptop could not send it) | already not sent | "Not sent · <why>" with **Edit** (back into the box) and Dismiss |

  Undo on a waiting message puts its text back in the box (or in the batch when the box has text, so nothing you typed is overwritten) and says "Undone: it was never sent". It is only ever said when whoever holds the message has proved it did not give it to the agent; when it answers "too late", the faded message says so and goes on to show the laptop's receipt. A full navigation to another session keeps a text-only hold in this tab and resumes its remaining window there, then delivers once to the original session. A same-session reload discards that handoff and keeps the draft unsent. Photo attachments stay safe across in-place switches, but a full navigation cannot carry their `File` objects, so the photo send is not resumed. A message Claude Code is already holding as a queued message is out of the reader's reach on purpose (the reader never sends a key to a pane); DESIGN.md, "Undoing a send", says what taking it back would involve. The answer sheet's Send is a separate page and has no Undo window.

Tap the line (elsewhere) or the chevron to bring the tabs and controls back. **On a phone (440 px wide or less) the header starts folded**, on every view, so a conversation or an HTML file has the screen; a choice made with the chevron is kept in this browser and wins over that, in both directions, and until one is made the header follows the width (a turned phone included). On a conversation the folded line also holds the three jumps of the controls (**↑ You** the message before yours, **You ↓** the next, **Ask ↓** the next reply that needs you; the keys `k`, `j` and `n` as before). Up to 640 px wide the folded header is two lines (the picker, the live badge, search and the chevron; then the jumps, the view icons, the answer sheet and Follow) and its Synced line shows only when it warns (a stale or failing sync; **Sync** is in the unfolded header). On a touch screen every control in the header is at least 44 px tall (and the icon buttons 44 px wide).
- **Search.** The magnifier beside the chevron, `/`, or Cmd/Ctrl+F opens a search row under the title. The browser's own find cannot see what the page folds away (wake-ups, working notes, the rest of a clipped reply) or has not drawn (every other conversation), so Cmd/Ctrl+F opens this search instead, and a second Cmd/Ctrl+F inside its box hands over to the browser's. Cmd/Ctrl+Shift+F opens it on all conversations. It matches plain text, case-insensitively, as typed (`fm/some-branch`, `c7639c`, a path, a port): every word must be in the same message, reply, working notes or tool steps, in any order, a "quoted phrase" stays together, and two characters are the least. **This conversation** tints every match on the page, the current one stronger, and counts messages ("4 of 37"; the tooltip gives the occurrences). **All conversations** searches the reading list and lists the matches (**List** brings the list back), the conversation with the newest match first and the newest match first inside it. **Anyone, You, Replies, Needs you** and **Firstmate** narrow whose words, **Tools** reads only the tool steps (what each says it did, its file and the first 100 characters of its command, so a branch, port or path that appears only in a command is found), and **Failed** only the steps that failed (a word in a step that worked does not count). Enter and Shift+Enter (or Cmd/Ctrl+G) step through the matches, a row in the list picks one, and Esc closes. A match opens only what hides it, in place, through the opener its own button uses: a run of folded wake-ups, a folded wake-up, a clipped message or reply, the working notes, the tool steps (all of them, not only the first 10). Closing folds back what the search opened and keeps your place. There is no index, no server route and no model: it runs on the turns the page already holds, so a query goes nowhere (the hosted copy, sealed or not, searches in the browser once the turns are open, and its "All conversations" covers the conversations this device has loaded, saying how many of the listed ones that is). While you search, the tabs and controls fold away as in the folded header, and Follow Herdr waits until the search is closed. **This conversation** belongs to the conversation it was opened in: switching to another conversation takes it off the screen (no query, no marks there), and it is there again, with its words, when its own conversation is shown again; each conversation keeps its own. **All conversations** is the only search that crosses conversations, and it stays on when you switch to a conversation with no search of its own. While the conversation on screen has its own search, All is off (the chip is dimmed and the key does nothing, saying why) until that search is closed with the ✕ or Esc; a conversation with its own search takes the screen back from an all-conversations search. A rebuild or Sync runs the query again without moving you and keeps the current match, and a reload for new page code keeps every search (query, scope, filter and match; each conversation's own too) in this tab. Highlights use the browser's CSS Custom Highlight API (Chrome 105, Safari 17.2, Firefox 140); without it the current message flashes instead.
- **Tool steps.** A reply's row reads "7 steps · edited 2 files · 1 failed" (the failures in red, and in words). It opens a list of one-line steps: a kind (`Ran`, `Read`, `Edited`, `Wrote`, `Searched`, `Asked`, `Agent`, `Skill`) and what it did, in the agent's own description of a command, else the command's first line, a path, a pattern, a URL or a question. Steps are grouped in runs of consecutive calls with the agent's working notes between the runs, the first 10 show and the rest sit behind "N more steps", and a failed step is red and says "failed". An edit or write shows `+3 −1`. A step opens a **sheet**, a bottom sheet at phone width and a dialog on a wide screen: its command or file (**Copy**), an edit or write as a diff with two lines around each change (12 lines, then "Show full diff"), its output as the last 12 lines ("Show all N lines": a command's error is at the end), **Prev** and **Next** through the turn's steps (the arrow keys too), and **Ask about this**, which is Reply with a pointer that names the step ("Re your step at 09:14 (Ran "Run the settings tests"): "). Rows and sheet buttons are 44 px at phone width and on touch screens. What is kept, by `prototype/tool_steps.py`: the summary (140 characters), the command (600) and the diff of an edit or write (1,500; a write's count is of the whole file) travel with the turn, read from `message.content` of the log's tool results and never from `toolUseResult`, the second copy of every output; a failed step's **last 400 characters** travel with the turn too; the output text (a command's last 1,500 characters, anything else's first 1,500) is its own object (below). **The text of a file the agent read is never kept**, and a call that touches a dotfile or a credential path (`.env`, `.npmrc`, `~/.ssh/…`, `credentials.json`, a command that names one) keeps its row, its failure marker and nothing of its text: no diff, no output, no tail. Turns from a copy built before steps were kept show the old "N tool steps" line. On the laptop's page a step's output comes from the server (`GET /api/transcript-reader/steps?conv=<id>`, which reads `out/steps/<id>.json`, written beside the page by the page build so the page itself holds none of it).
- **Cleared sessions.** `/clear` starts a new session log in the same pane. The reader joins the sessions a pane ran into one conversation, under the newest one, with a divider at each clear: the log it cleared is the one written within two minutes before the `/clear` that names the same remote-control link, in any project folder (a session resumed from another directory keeps its old folder), else the log the same Herdr pane ran before, whose last dated record is nearest before the `/clear` and which was written at or after it (a session cleared, then exited and resumed with `claude --resume <new id>`, has no link, and exiting writes to its old log well past the clear), else the one written then in the same folder. Naming any of them (`#s=…`, `reader.py add`) opens the whole conversation, and `reader.py` adds the newest one to the reading list. Replying to a turn from before a clear goes to the pane's current session, and the message names the earlier log, since that session never saw the turn. Claude started again in the same pane (Firstmate swaps a worker's model that way) joins the same way, when the new session starts within ten minutes of the old log's last write. A log is also written to long after its last turn (a Herdr restart rewrites the link and cost records, which carry no time), so the time of its last dated record counts as well as its modification time, and a `/clear` made hours after the last turn still names the log that holds the same remote-control link. Herdr keeps the first session id it was told after such a restart, so for a Claude pane whose id no running Claude holds, the reader asks Herdr for the pane's foreground process and reads that process's session from Claude Code's own record (`~/.claude/sessions`); a pane back at its shell runs no session.

## Links to one message

The page's address names a conversation, and a document or a message in it:

| Address | Opens |
|---|---|
| `#s=<session id or its first characters>` | the conversation (the page writes this itself as you read) |
| `#s=<session>&d=<document id>` | its Documents view on that file |
| `#s=<session>&m=<turn id or its first 6 or more characters>` | the conversation, scrolled to that turn's reply (its message when it has no reply), outlined for a moment |

The turn id is the id the session log gives the turn (`uuid`), so it holds across rebuilds, restarts, `/clear` (the session in `s=` may be any session of the pane's chain) and the move from one build to the next. What hides the reply is opened in place: a wake-up folded into a run, a folded wake-up, a clipped reply. An id the conversation does not have opens the conversation and says so in the line under the header; a session not on the reader says that, and the page stays where it was. The page goes back to `#s=` once it is there, so the same link works again and a reload does not jump again.

**The page follows an address that reaches it while it is open, without loading again.** A link opened over the conversation on screen, an address pasted into this tab, a pin in another tool: another conversation, a Documents view or a message in it is shown in place, as a fresh load would show it (a closed pane's conversation is listed again, a `/clear` chain opens under its newest session, the same notices). The page's own address writes (`history.replaceState`) fire no change, so following never calls itself, and an address for the conversation already on screen changes nothing. A link in a reply still opens in a new tab, as every link does.

`message_link.py` writes the address of a message for a reminder:

```bash
python3 setup/transcript-reader/message_link.py <session id or prefix> [--from-session <session id or prefix>] [--since <ISO date/time>] <text>
python3 setup/transcript-reader/message_link.py <session id or prefix> --message <id>    # check an id and write its address
```

```
local:   http://localhost:8768/setup/transcript-reader/out/prototype.html#s=9322c689&m=5e6f7a8b-9c0d
tailnet: https://<machine>.<tailnet>.ts.net:8443/setup/transcript-reader/out/prototype.html#s=9322c689&m=5e6f7a8b-9c0d
```

Only the agent's replies are looked in (never your messages or a steering message), across the whole `/clear` chain of the session, oldest first, as a plain case-sensitive match. Use `--from-session` to start at a session in that chain, including newer sessions, or `--since` to start at an ISO date or date/time. When no scope is given, the whole chain is searched as before. If a key occurs in more than one agent reply, the oldest address is returned with a warning on stderr that lists every match's session, UTC time and message id; scope the search to choose the intended call. The warning and address contain no message text. The tailnet name is what Tailscale reports (`tailscale status --json`), the ports are `PMOS_READER_PORT` and `PMOS_READER_HTTPS_PORT`; with no tailnet name the tailnet line says so. It exits 0 when an address is printed, 1 with a sentence when the session or the message is not found and 2 for a wrong command line, reads the session logs only and prints ids, times and addresses, never the words of a message. The tailnet address works when the reader was started with `--tailnet-https`. A reminder can carry both, as `[Mac](local) · [phone](tailnet)`.

### The fleet timeline is off for now

The page's **Fleet timeline** tab is switched off: the build skips collecting the fleet records (a large part of the page and of every rebuild) and the page hides the tab. All its code, styles and tests stay. To bring it back, set one environment variable where the reader's server or `reader.py` is started, then restart (`serve.sh restart`):

```bash
PMOS_READER_FLEET_TIMELINE=on serve.sh restart      # on, 1, true or yes; unset or anything else is off
```

The offline copy (`sync.py`) follows the same switch (one reader of the variable, `fleet_timeline_on()` in `build_prototype.py`). Off, a build collects no fleet records, writes no `f/<yyyy>-W<ww>.json` week and lists none in `index.json` or the manifest, the next build removes weeks an earlier build wrote, and the offline page hides the tab (`index.json` carries `"fleet_timeline": false`; an index without it, from before the switch, keeps the tab). On, the output is what it was before the switch. A build run with the switch changed parses the conversations again, so it takes effect at once.

### Which conversations the offline copy holds: `--panes`

By default the copy holds conversations running in a live Herdr pane at build time plus every starred conversation (`--panes open`). `--panes all` remains available for an explicit history copy that includes other closed panes. It works with `--build-only`, `--seal`, `--launch-agent` and `--preview`:

```bash
python3 setup/transcript-reader/sync.py --preview --panes open              # what it would include and leave out; nothing is written
python3 setup/transcript-reader/sync.py --build-only --panes open
python3 setup/transcript-reader/sync.py --launch-agent --panes open         # the printed command carries --panes open
```

- **Default is `open`.** The phone copy contains the sessions Herdr reported as live when that build ran and every starred session. A starred session that was not live remains readable, but its picker option is historical rather than live. The index carries the matching stars for every session it holds. Use `--panes all` when an explicit history copy is wanted.
- **Narrowing prunes.** A conversation the scope drops is not parsed, its object, its documents (unless a kept conversation names them) and its answer sheet are removed from `out/hosted/` by the next build, and from the sealed bucket by the next `--seal`'s existing prune. Widening brings them back at the next build.
- **Your own `~/workspace` sessions have no Herdr pane,** so `open` leaves them out. `--panes all` includes them when they are in the selected workspace scope.
- **With no live pane at all** (Herdr not running) `open` would leave nothing and the prune would empty the copy, so the run stops with a message and changes nothing.
- **`--preview`** builds, seals and writes nothing and asks for no passphrase. It prints counts (live pane, reopened, closed; how many fall in the sealed copy's 90 days), an estimate of the conversations' size (scaled from what a build here already wrote, else a rough 2% of the logs' size; documents, answer sheets, fleet weeks and the page are extra), how many conversations an earlier build wrote that this scope would remove, then a table of the included conversations only (Herdr label, home, pane open / reopened / closed, last activity) and the count of those left out. The label is the one Herdr shows: the pane's label, else its tab's label, remembered in `pane-labels.json` for a pane that has closed; the terminal title or an 8-character id stands in only when no label is known. `--show-left-out` also lists the left-out conversations. It takes the same options as a build (`--panes`, `--reading-list`, `--session`, `--no-workspace`, `--main-home`).

The LaunchAgent that `sync.py --launch-agent` prints runs the build from launchd's own environment, which holds none of your shell's variables, so the printed plist carries the switch: print it with the variable set (`PMOS_READER_FLEET_TIMELINE=on python3 setup/transcript-reader/sync.py --launch-agent`) and its `EnvironmentVariables` holds `PMOS_READER_FLEET_TIMELINE=on`; print it without and the agent builds without the timeline. Install the printed plist again after changing the switch.

## Open it from the phone

The reader can also listen on this Mac's Tailscale address, so a phone on the same tailnet opens it directly, with no SSH tunnel. It is off unless you ask for it, and it asks for a passcode.

```bash
bash setup/transcript-reader/serve.sh passcode              # once: type a passcode (8+ characters) twice, nothing is shown
bash setup/transcript-reader/serve.sh restart --tailnet     # or start --tailnet; PMOS_READER_TAILNET=1 is the same switch
bash setup/transcript-reader/serve.sh status                # "Tailnet address served: http://100.x.y.z:8768 (passcode required)"
```

Then open `http://<the Mac's Tailscale address>:8768` on the phone (`tailscale ip -4` prints it), type the passcode and it opens the reader.

- **What listens.** Loopback as before, plus the address `tailscale ip -4` gives, on the same port. Never `0.0.0.0` or another interface (the server refuses any address outside Tailscale's 100.64.0.0/10). If Tailscale is not running, or no passcode is set, it starts loopback only and says why in one line.
- **The passcode.** `serve.sh passcode` reads it from the terminal without echo; it is never an argument, printed or logged, and there is no default. Only a salted scrypt hash is stored, in `out/passcode.json` (owner-only, gitignored with the rest of `out/`; `PMOS_READER_PASSCODE_FILE` names another file). A new passcode signs every phone out at once, and so does removing the file. The Herdr organizer page on port 8765 uses this same passcode and file (below): one passcode, one sign-in for both.
- **What a signed-in phone gets.** A correct passcode sets a session cookie (`pmos_session`: HttpOnly, SameSite=Strict, a random token whose hash names a small owner-only file in `out/passcode.json.sessions/`), so a server restart keeps the phone signed in, and a session ends after 30 days without use. The cookie is on top of the usual checks: every page and API route, Send and pins included, still needs the Host and Origin to be exactly the tailnet address and port, Fetch-Metadata and the page's token. Requests on `localhost` need no sign-in, as before.
- **What works from the phone.** The whole reader, the message bar included, as on the Mac: the live badge, Sync, Follow Herdr, Pins (kept on the Mac), the Documents tab, and every way to send to the session's Herdr pane (a message, with photos from the phone's library or camera, with the Send button, Reply, "Comment on this", the batch with Add then Send, "Message about this file", the answer sheet's Send, and a `/` command after its confirm). The page counts as served, and so enables all of it, on `localhost` or on a Tailscale address (100.64.0.0/10) with the token the server writes into the page; a file copy or any other address stays read-only. If the Mac's server restarts, the page reloads once to pick up the new page token (a draft in the box is kept), and the phone stays signed in; after a new passcode it reloads to the passcode page and a correct passcode brings the same page back. On a touch screen Send, Add, the links under the box and the Pin and Reply pills are 44 px (Pin and Reply 34 px) tall.
- **Wrong passcodes.** The third wrong one in a row from an address locks it for 30 seconds, and each after that doubles the lock up to 15 minutes.
- **When it will not open.** The passcode page says why in words (a wrong passcode, a lock and its wait, a refused request, no answer within 10 seconds, a cookie the browser did not keep, a script that did not start), and every attempt is one line in `out/server-<port>.log` on the Mac: the time, the phone's address and the outcome, never the passcode.
- **Sign out.** Open `http://<address>:8768/transcript-reader/signout` (the page at `/transcript-reader/signin` shows a Sign out link while you are signed in). It ends the sign-in for the organizer page too.
- **Not covered.** This address is plain HTTP: Tailscale encrypts the traffic between the devices, but the browser shows no padlock and the cookie has no `Secure` flag. For the https address, and an offline copy the phone keeps, see "Read it with the laptop shut". Anything else on the tailnet can reach the port and see the passcode page, which is why the passcode is required. A browser on the Mac itself may be sent through a corporate proxy that blocks tailnet addresses; use `localhost` there.

## Read it with the laptop shut

The phone can keep the sealed copy (below, "The sealed copy") and read it with the laptop closed or asleep. Nothing is hosted: the phone downloads the copy from this Mac over Tailscale while the Mac answers, stores it on the phone, and opens it from there when the Mac does not. A phone browser only stores a copy for offline use (a service worker, on-device storage) and decrypts in the page (WebCrypto) on a secure address, so the phone address needs HTTPS. Tailscale issues the certificate for the machine's own `https://<machine>.<tailnet>.ts.net` name; the reader serves it itself, and the passcode sign-in is still required on it.

### Your steps, in order

1. **Keep a sealed copy.** Once: `python3 setup/transcript-reader/sync.py --seal` (it asks for a passphrase; `--launch-agent` prints a LaunchAgent that keeps the copy fresh while the Mac is awake, see "The sealed copy"). The passphrase is the phone's key; the passcode is the sign-in.
2. **Turn on Tailscale HTTPS certificates** for the tailnet: Tailscale admin console, DNS page, HTTPS Certificates. It is off until you do this.
3. **Restart the reader with the new switch** (a passcode must be set, `serve.sh passcode`):

   ```bash
   bash setup/transcript-reader/serve.sh restart --tailnet-https
   ```

   It reads the machine's name from Tailscale (`tailscale status`, never typed in), asks Tailscale for the certificate (`tailscale cert`, kept owner-only in `out/tailnet-cert/`) and prints the address to use: `HTTPS address served: https://<machine>.<tailnet>.ts.net:8443 (passcode required)`. The plain `http://<tailscale address>:8768` keeps working beside it until you stop using it. If certificates are off or none can be had, it starts as before and says why in one line.
4. **Open that `https://...ts.net:8443` address on the phone** and **sign in** with the passcode. Then tap **Offline copy** (beside Sync on the reader page), or open `https://<machine>.<tailnet>.ts.net:8443/setup/transcript-reader/out/bucket/index.html` directly, and enter the passphrase ("Remember on this device" keeps the key, never the passphrase).
5. **Add to Home Screen** from the sealed copy's page (Share, then Add to Home Screen), so iOS does not clear its storage. The Home Screen app keeps its own storage, apart from Safari's: if it asks you to sign in and for the passphrase again, do that once there, and do step 6 in it.
6. **Tap Download everything now.** It shows the progress and, when it ends, how much is stored. From then on the page keeps what it holds current by itself, fetching only what changed, whenever the Mac answers.

The port is 8443 because macOS lets only root listen below 1024, so the address needs it (`--https-port` or `PMOS_READER_HTTPS_PORT` change it). The certificate lasts 90 days: `bash setup/transcript-reader/serve.sh cert` renews it and a running reader takes it up within the hour (a restart with the switch renews it too). `serve.sh status` shows both addresses. **If you rename the machine in Tailscale**, restart the reader with the switch (the address is its new name) and press Download everything now on the phone again: the phone keeps what it stored under the old address, which the new address cannot see.

### What the copy holds, and how fresh it is

- **What is in it.** By default, conversations whose Herdr panes were live at the build and every starred conversation are carried, along with the markdown, HTML and image files they name, the fleet timeline weeks (when the timeline is switched on), the answer sheet's questionnaires and each conversation's tool output (`t/`, below): everything `sync.py --seal` seals (the sealed copy section). The index carries the stars that name every carried conversation. A starred conversation that was not live is readable on the phone, but is not labeled live. `--panes all` explicitly includes the broader history scope. Everything is redacted before it is sealed.
- **Freshness.** The phone's copy is as new as the last time the phone could reach this Mac, and that is as new as the Mac's last sync (every minute with the LaunchAgent while the Mac is awake; a sleeping Mac builds nothing). With the Mac away the page says `Offline · copy from 14:02 (3 h old)` and Herdr states are as of then. Replies to turns after that are not on the phone until the Mac is back. The copy keeps 90 days, so what the Mac drops from them leaves the phone at its next download.
- **What builds the copy.** Only `sync.py` writes it, and nothing here runs it by itself: the printed LaunchAgent (below, "The sealed copy") is the owner's to install, and until it is, the copy is as old as the last build somebody ran. The phone's **Sync** is the other way: it asks this Mac's reader server to build the copy now (`POST /api/transcript-reader/copy-sync`, `copysync.js`: `sync.py --seal` for the sealed copy, `--build-only` for the plain one, in a process of its own, one build at a time), waits ("The laptop is building a new copy…"), and then reads it. The server never holds the passphrase: `sync.py` reads it from the login keychain item the LaunchAgent uses (`security add-generic-password -s pmos-hosted-reader -a "$USER" -w`) when it has no terminal and no `HOSTED_READER_PASSPHRASE`. A build that cannot run says why on the page's line ("The laptop could not build a new copy: ..."): no keychain item, another build running (a build by hand or the LaunchAgent: `sync.py` takes its own lock), a seal that stopped part way ("Sealing stopped (ENOSPC: no space left on device, write); the sealed copy keeps what it had.": the sealing step's own reason, never a line of a conversation), or a server that has not been restarted since the route came (`serve.sh restart`). The build uses the live-plus-starred default; to build with options (`--panes all`, `--no-workspace`), set `PMOS_READER_COPY_ARGS="--panes all"` where the server is started, as for `PMOS_READER_FLEET_TIMELINE`. The same build sends what the phone queued (`drain.js`), so a Send made while the Mac was shut goes out at the next Sync as it would at the LaunchAgent's next run. A page the reader's own server did not serve (a static host) has no server to ask, and its Sync reads the newest copy there is.
- **What the phone holds.** Sealed bytes and the key (not extractable), never the passphrase and never any text in the clear. The shell page, a manifest and an icon are cached so the Home Screen app opens. **Forget this device** clears the key, everything stored, the cache, the worker and any message still held, and asks the passphrase again.
- **Not offline.** Search, pins, the Fleet timeline (when switched on) and documents all work from the stored copy. Follow, Sync from Herdr, reopening a closed pane and the local page's live state need the Mac (and the local reader page itself is not stored).

### Send with the laptop shut

A Send made while the Mac cannot be reached is held on the phone, sealed, and the bar says "Held on this phone". When the Mac answers, the phone posts it to the reader's queue (`/api/transcript-reader/queue`) under the id it already has, and from there it is the same Send as ever: `drain.js` carries it out at the next sync, never twice, with its receipt shown on the phone. The same rules apply: a message the Mac has not received within 12 hours of being written is dropped and said so, and a message the Mac already has is not queued a second time. The queue accepts at most 50 waiting messages.

A held message can be taken back (Undo on the faded message). The phone cannot know whether an earlier post of it reached the laptop with only its answer lost, so Undo marks the held message "cancel" and tells the laptop when it answers: the laptop then either takes the message out of its queue or leaves a note that refuses a late copy ("cancelled"), or says it already has it ("too late", and the receipt follows). Until it answers, the message stays on screen as "Undoing · waiting for the laptop to confirm", and its text is not given back.

### HTML files in the copy

An HTML file a reply or message names is in the copy under the same name rules (the same `.html` and `.htm` names, found the same way), location rules (under your home folder or the temp folders, after links are followed) and size rule (8 MB) as in the local viewer, and opens in the Documents tab in a frame with the same limits: the file's own scripts and styles run, in an opaque origin that cannot read the reader, its storage or its cookies, and with no network, frames or forms.

- **Beside the file.** What the file loads from beside itself is folded into it when the copy is built, under the viewer's rules: pictures (`.png .jpg .jpeg .gif .webp .avif .svg .ico .bmp`), stylesheets (`@import` and `url()` too) and scripts, only below the file's own folder, never a dot file or folder or a link leading out, and a file directly in the home or a temp folder gets only its own folder's files. A script with `defer` or `async` runs at the end of the body, in order. Per file at most 12 MB is folded in.
- **What does not load**, as in the local viewer or because the copy is one file: fonts, audio and video; other pages (a link to another page beside the file); module scripts; `https://` addresses and `/rooted` paths (the frame has no network); anything a script asks for while it runs (`fetch`, an image made in code); inline SVG's own `<image>` and `<use>`; and anything over the 12 MB budget or the viewer's 32 MB limit for one file. What is left out is listed in the document's object (`skipped`).
- **How it is shown.** The frame has no `sandbox` attribute: a sandboxed frame is not served by a service worker, so the worker answers the frame itself and sends the policy the laptop's own viewer sends (`sandbox allow-scripts; default-src 'none'; ... connect-src 'none'`), which makes the document sandboxed by the response. The file's text never leaves the page except into that one response, and with no worker answering the address does not exist, so a file is never shown unsandboxed.
- **As of the build.** The file is as it was when the Mac built the copy, not as on disk now. Reload shows the copy again.

### Images in the copy

An image a reply or message names is in the copy under the same name rules, location rules (under your home folder or the temp folders, after links are followed) and file types as in the local viewer, but with limits of its own, because the copy is carried on a phone: **2 MB for one image** and **12 MB for all of them** (the newest files are carried first). The viewer's 10 MB would otherwise put a Retina screenshot of a long page into every copy. An image over a limit is still offered: its button is there, and it opens to a line saying that the picture is not in the copy, how big it is and which limit it is over (open it on the laptop).

- **How it is carried.** As its own object (`d/<id>.json`, like any document) holding the file's bytes in base64, so it is a third larger than the file, and unlike text it does not compress when the copy is sealed. It is shown in an `<img>` from a `data:` address, which needs no service worker, so it also works over plain `http` (the page's policy allows `data:` images in the copy only, for the reader page only; the answer sheet's policy is unchanged). An SVG is shown the same way, so its scripts do not run.
- **What it costs, on the real data.** On this Mac's 590 conversations (826 documents), 17 images were named, 4.1 MB on disk and the largest 0.73 MB; none is over a limit. They add 5.5 MB to the 99 MB of objects before sealing (+5.5 %), and about 4.0 MB to the 35 MB the sealed copy is after it (+11 %, since the text compresses and the pictures do not). The limits bound the growth at 12 MB of pictures (16 MB as base64).
- **Not redacted.** Redaction is a pattern scan of text for secrets (`redact.py`); it cannot read pixels. A screenshot that shows a token or a private page goes into the sealed copy as it is, as the pictures of an HTML file do, under the same encryption. An SVG's text goes through the scan.
- **No "Open alone" in the copy.** A tab opened on a `blob:` address would run an SVG's scripts in the reader's own origin, so the copy offers Full size and the phone's pinch-zoom instead.
- **As of the build.** The picture is as it was when the Mac built the copy.

### Tool steps in the copy

The steps of a turn (their summaries, commands, diffs and a failed step's last 400 characters) are in the conversation's own object, so a conversation read once on the phone shows its steps and its failures with the laptop shut. The output text is not: it is one object a conversation, `t/<id>.json` (`{ outputs: { "<turn id>:<n>": text } }`, each up to 1,500 characters, never the text of a file read, none for a step that touched a dotfile or a credential path), redacted and sealed like the others. The page fetches it when a step opens, once per stamp, and keeps it on the device (`hosted.steps`).

- **7 days, computed at the build.** `index.json` carries `steps_from`, the build's time less 7 days (it moves every build, so it is left out of what decides whether the index is sealed again). A step made after it is **recent**: its conversation's output is part of "Download everything now" when the conversation was last active after it, and is fetched when the step opens. A step before it shows "No output on this device for this step. Output stays here for the last 7 days; older output waits at the laptop." and **Download this conversation's outputs**, which fetches the conversation's object (all of its outputs, old ones too) and keeps it; the next "Download everything now" does not take it away. A failed step's last 400 characters are shown under it either way.
- **With the laptop shut.** A step whose output is not on the device says "No output is stored on this device for this step, and the laptop is not reachable" and offers the download again ("Try again" goes to the laptop at once, though it was away a moment ago). "Everything is on this device" adds that the output of older conversations stays at the laptop until a step asks.
- **Secrets.** Every string of every object, `t/` too, goes through `redact.py` when sealed (the counts are in `out/hosted/redactions.json`, by object). Output carries more shapes of secret than prose does, which is why a file read's text is not kept at all and a command's output is capped.
- **Search.** The steps of a conversation the device has loaded are searched inline (summaries, files and the start of a command). Full commands and output are not: they would add about a fifth to the sealed copy, and the output is not on the device unless a step asked for it.
- **What it costs.** Measured on this Mac's logs (read only, built into a scratch folder: 658 conversations, 46,551 steps, of which 1,411 failed, 3,017 are file reads and 5,210 touched a dotfile or a credential path): the steps in the conversation objects take them from 12.7 MB to 17.6 MB gzipped (+4.9 MB, +39%; 39.3 to 63.1 MB raw), of which the commands are 2.8 MB, the diffs 0.65 MB, the failed steps' tails 0.11 MB and the summaries, files, times and keys the rest. The `t/` objects are 650, 35,675 outputs, 30.8 MB raw and 8.8 MB gzipped in the bucket on the laptop, of which 5.8 MB belongs to the 355 conversations active in the last 7 days, so **Download everything now** carries about 10.7 MB more than before (4.9 + 5.8) and the bucket about 13.7 MB more. The earlier research's "+5%" was for summaries alone; the commands are the bulk of the difference. A command cap of 300 characters in place of 600 would save about 1.0 MB gzipped, and 150 about 1.9 MB. No file read has any text in any object, and no step that touched a dotfile or a credential path has a diff, a tail or output.

## Open the Herdr organizer from the phone

The Herdr workspace organizer page (`apps/wip-herdr-workspace-organizer.html`) is served by the shared app server, `setup/serve.sh`, on port 8765. It can listen on the same Tailscale address as the reader, with the same passcode and the same sign-in: signing in to either app signs the phone in to both, and signing out of one signs out of both. It is off unless you ask for it.

```bash
bash setup/transcript-reader/serve.sh passcode    # once, the same passcode as the reader (skip it if the reader's is set)
bash setup/serve.sh --restart --tailnet           # or start --tailnet; PMOS_SERVE_TAILNET=1 is the same switch
bash setup/serve.sh status                        # "Tailnet address served: http://100.x.y.z:8765/apps/wip-herdr-workspace-organizer.html"
```

Then open `http://<the Mac's Tailscale address>:8765/apps/wip-herdr-workspace-organizer.html` on the phone (`tailscale ip -4` prints the address), type the passcode and the page opens. Restarting `setup/serve.sh` restarts the shared server for every app it serves; they come back on loopback as before.

- **What listens.** Loopback as before, plus the Tailscale address on port 8765, with a request handler of its own that serves only the organizer page, its API (`/api/herdr-organizer/*`), its Refresh snapshot route and the sign-in. Every other path, the other apps and every file of the repo included, answers 404 there, signed in or not. Never `0.0.0.0` or another interface. If Tailscale is not running, or no passcode is set, it starts loopback only and says why in one line.
- **The passcode.** The reader's (`PMOS_READER_PASSCODE_FILE`, else `setup/transcript-reader/out/passcode.json`); `setup/serve.sh` has no passcode command of its own.
- **Every guard stays.** The page's API still needs the Host and Origin to be exactly the tailnet address and port, Fetch-Metadata, JSON bodies, the per-start token and one change at a time, plus the sign-in. Everything the page can do on the Mac it can do from the phone, restarts and switch files included, each behind its own confirm as before.
- **At phone width.** On a touch screen every button, tab, field and checkbox row is at least 44 px tall, and long commands wrap. The page loads its fonts from Google, so the phone needs internet access as well as the tailnet.
- **When it will not open.** The passcode page says why in words, and each sign-in attempt is one line in `/tmp/pmos-serve-8765.log` on the Mac. A browser on the Mac itself may be sent through a corporate proxy that blocks tailnet addresses; use `localhost` there.
- **Sign out.** `http://<address>:8765/herdr-organizer/signout`.

## The lite page and the glance feed

For watching several conversations at once (Conn's columns, at most three, and its list of open asks, built against the formats below), every build that writes the reader page also writes, beside it, what a page that shows **one** whole conversation needs (its turns, its documents and its answer sheet), and one small file that says which conversations ask you something. Neither makes the build parse anything more: a conversation's object is its own bytes, written only when they changed.

### The lite page

```
http://localhost:8768/setup/transcript-reader/out/live/index.html#s=<session id, or its first 8 characters>
```
The same address forms as the reader page (`#s=<id>&d=<document id>`, `#s=<id>&m=<turn id>`, "Links to one message"), on `localhost`, the tailnet address and the https address alike, served and token-filled like any page (opened in a tab or a web view, never framed). It is the reader page's own code in a third mode, so it draws the conversation exactly as the full page does, and it loads **only the conversation it is opened on** (one object, 0.1 to 4.3 MB on the owner's data) instead of the 34 MB page. A conversation picked in its session picker loads when it is picked.

It is a served page in every other way: it **sends straight to the pane** through the same `send` route and every check the server makes (Herdr's state, the foreground process, the session, one message at a time, the 5-second Undo window in the page), takes **Reply**, **Comment on this**, batches and photos, **follows Herdr** when asked to, polls the state every 2 seconds for each pane's agent state, waits on `events` for a new build and takes it in about 1.5 seconds, has Pins, Stars, Search in the conversation, **Documents** (all of them, below), the **answer sheet** (below) and **Sync**. A column is therefore the whole of one conversation: nothing in it needs the full reader. What differs from the full page:

- **Follow is off** until you turn it on in the page; the setting is the page's own (`tr-live-follow` in the browser's storage, apart from the full page's `tr-follow`), so a column pinned to one conversation stays on it.
- **Search "All conversations"** looks in the conversations the page has loaded, and says how many (the others load when opened). No server route searches.
- **Documents** lists the files the conversation names (markdown, HTML, pictures) and, for a leader's conversation (a run in a Firstmate home), every file of the home's task folders, named or not (`data/<task id>/`, the same files and the same By task and By folder views as the full page, with each task's title and state). A markdown file opens through `md-open`, as it is on disk now, and an HTML file or picture through `html-open` and `image-open`, as everywhere. They come in the conversation's own object, so opening Documents loads nothing more. A task folder is cut at 400 files, as in the full page, and says how many it left out.
- **The answer sheet** is the lite sheet, `out/live/sheet.html`, in the same window as the page (below). A reply that asks for keyed answers has its "Answer sheet →" button as in the full page, and the title bar's link goes to this conversation's sheet; both open the lite sheet, never the full reader's `questionnaire.html`, and the sheet's "← Conversation" comes back to `#s=<id>`.
- **No offline copy**, no Fleet timeline (the hosted copy has both; this has neither), and no Sync of a copy.

### The lite answer sheet

```
http://localhost:8768/setup/transcript-reader/out/live/sheet.html#q=<session 8>:<time the reply was written>
http://localhost:8768/setup/transcript-reader/out/live/sheet.html#s=<session id, or its first 8 characters>
```

The answer sheet's page (`prototype/questionnaire.html`) in the same third mode as the reader page: no transcript in it, it loads `live/index.json` and then `live/a/<conversation id>.json` (the conversation's questionnaires, as the hosted copy's `a/` object holds them), and it shows **only the conversation its address names** (`#q=` is what the reply's button writes, `#s=` what the title bar writes; with neither it lists every conversation's). It is served and live like the local sheet: the cards, **Fill recommended**, **Copy**, and **Send**, which goes straight to the pane through the same `send` route with every check the server makes (Herdr's state, a pane at a permission prompt, the foreground process, one message at a time, and a sent line is not sent twice); the pane it sends to is Herdr's, polled every 2 seconds; a new build is taken where it stands (not while a box is typed in or a send is under way), and the sheet answers "Answered" once the session holds the keyed line. Its "← Conversation" link is `index.html#s=<id>`. The page is opened in the window or column the conversation is in, which stays that conversation's; nothing in it leaves for the full reader.

The page needs a server started after this change (`serve.sh restart`: the routes are in `api.js`) and one build after it (`reader.py rebuild`, or any change a page is open for), which writes `out/live/`.

### What a build writes

| File | Holds |
|---|---|
| `out/live/index.html` | The lite page: no transcript in it. |
| `out/live/index.json` | The hosted index's shape (`hosted.js` reads it): `as_of` (the build time, which is the page's own stamp), `template` (the page's code hash: a page whose own differs reloads), `conversations` (below), `closed` (panes closed in the last two weeks, to offer under "Closed panes"), `fleet_timeline: false`, empty `documents`, `weeks`, `summaries` and `stars`, `sheet_template` (the lite answer sheet's code hash, as `template` is the page's) and `sheets` (one entry for each conversation that has an answer sheet, by its id: `{ object: "a/<id>.json", stamp, list: [{ at, open, title }] }` where `open` is how many cards no keyed answer covers yet; the hosted index's shape). |
| `out/live/s/<id>.json` | One conversation, exactly its entry in the reader page's payload (the same bytes) less `pane` and `reopened`, plus `documents`: the files it lists, by id in id order, each as the page lists it without its `text` (`{ id, name, path, dir, mention, mtime, lazy: true }` for a markdown file, `{ ..., kind: "html" or "image", size }` for the others). The files are the ones its messages and replies name and, for a leader's conversation, every file of its home's task folders (a document whose folder is under `<home>/data/`, which is what the page's By task view lists). |
| `out/live/md-files.json` | id to path of those markdown files, which `md-open` reads as they are on disk when one is opened (never served). |
| `out/live/sheet.html` | The lite answer sheet: the sheet's page in mode `live`, no transcript in it. |
| `out/live/embed.html` | The embed page (below): the reader page's code in mode `embed`, for a host web view that hands it one conversation. No transcript, no token. |
| `out/live/a/<id>.json` | One conversation's answer sheet: `{ "questionnaires": [...] }`, exactly what the hosted copy's `a/<id>.json` holds (each questionnaire with its cards, the reply it came from, and the keyed answers you sent after it). Written only for a conversation whose reply asks for keyed answers, and only when its stamp changed. |
| `out/glance.json` | The glance feed, below. |

`index.json`'s `conversations`, newest activity first, one for each conversation on the reading list: `home`, `id` (the newest session's id), `ids` (every session of the conversation, oldest first), `file`, `where`, `last` (the newest turn's time), `order`, `turns`, `needs` (replies that ask you, with nothing from you after them), `pane` (the Herdr pane as of the build: `label`, `title`, `herdr`, `pane`, `status`, `live`; `live: false` is a pane that has closed, with the last label and state seen), `reopened`, `object` (`s/<id>.json`) and `stamp` (a hash of that object's bytes: a page keeps a loaded conversation while its stamp is the same).

The files are written before the page's stamp (the last file a build writes), so a page woken by a new stamp finds them; a conversation's object is written only when its stamp changed, and a restarted worker does not write them again; an object no listed conversation has is removed. Like everything in `out/`, they are the owner's alone (0700 and 0600). They are served to the lite page and its sheet only, to their own token-bearing fetches: `live/index.json`, `live/s/<id>.json` and `live/a/<id>.json` and nothing else under `live/` (the two pages, `live/index.html` and `live/sheet.html`, are served like any page, in a tab, never in a frame).

### The glance feed: `out/glance.json`

The glance feed says which conversations ask you something, for a native client's list of open asks (Conn's left panes). One small file (about 0.5 KB for each conversation: 16 KB for the owner's 31) that the client reads as a file, as Conn reads `stars.json` and `pane-labels.json`: no HTTP, no token. It is replaced whole through a rename, so a read never sees half of it, and it is written **only when its content changes** (a Herdr state change alone is not one: the feed holds no pane state), so its modification time says "an ask came, went or changed" and an unchanged build leaves it alone.

```json
{
  "as_of": 1793862812.17,
  "version": 1,
  "conversations": [
    {
      "id": "0f1e2d3c-...",
      "ids": ["0a1b2c3d-...", "0f1e2d3c-..."],
      "home": "main",
      "where": "",
      "last": 1793860599.0,
      "open_asks": 1,
      "ask": { "at": 1793860599.0, "uid": "t12ad57c7c69734480c8aaddb", "lines": ["Should I approve the 3 refunds over the cap?"], "tags": ["+1 earlier"] },
      "pane": { "label": "billing", "herdr": "work", "live": true }
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `as_of` | The build time (seconds since the epoch) of the build that last changed the file. |
| `version` | The format's version: 1. A reader that does not know it should ignore the file. |
| `conversations` | One record for each conversation on the reading list, newest activity first. The list of open asks is the records with `open_asks > 0`; the others are there so a client sees an ask go. |
| `id` | The conversation's id: the newest session of a pane's sessions across `/clear`. The lite page's `#s=` takes it or its first 8 characters. |
| `ids` | Every session id of the conversation, oldest first (Herdr's `agent_session` may name any of them). |
| `home` | The home the conversation runs under: `main`, a second mate's id, or `workspace` (your own sessions). |
| `where` | `""` for the home's own folder, `worker copy` for a worker's isolated copy, else the folder inside the home. |
| `last` | When the newest turn (your message or its reply) happened. |
| `open_asks` | How many replies ask you something with nothing from you after them: the count the page's header and the sidebar call "need you". |
| `ask` | The newest open ask: `at` (when its reply was written), `uid` (the turn's id, which the page's `#s=<id>&m=<uid>` address opens the conversation on; `null` for a turn with none) and `lines`, up to 3, each at most 200 characters: the questions of the reply's answer sheet when it opens one, else the lines of the reply that ask, and `tags`, what a list shows beside the lines, in the page's own words: `Answer sheet · N questions` when the reply opens a sheet, and `+N earlier` when N other asks are still open before this one (an empty list when neither). `null` when no ask is open. |
| `pane` | Which Herdr pane runs it: `label` (the name Herdr shows), `herdr` (its session), `live` (`false` means the pane has closed and `label` is the last one seen). `null` when no pane was ever seen for it. |

An ask is opened in a column or a window at `out/live/index.html#s=<id>&m=<uid>` (a document: `&d=<document id>`), and its answer sheet, when it has one, at `out/live/sheet.html#s=<id>`; all three are served at `http://localhost:8768/setup/transcript-reader/` as above. A pane's state (idle, working, blocked) is not in the feed: a client that shows it uses Herdr's own live state, which the feed would only repeat late. An ask's lines, its count and the conversation's last turn are computed by the reader's rules (the page's "Needs you" chips and ask boxes come from the same turns), so a list and the page agree.

### The open-asks route: `GET /api/transcript-reader/open-asks`

The glance feed as a route, for a client that lists the asks against its own rows (Conn's agents) and already knows which pane each row is. It answers one entry for each **live Herdr pane whose conversation has an open ask**, newest ask first. Nothing is worked out in the route: the feed (above) says which conversations ask and what, by the page's own rules, from the same turns and answer sheets; Herdr, read as the `state` route reads it, says which pane runs each one. A conversation counts only while a Herdr pane runs one of its sessions (a pane that has closed has no row), and a pane has one entry, its newest ask. The feed is parsed again only when its file changed.

```json
{
  "status": "ok",
  "generated_at": "2026-11-06T16:40:12.000Z",
  "as_of": "2026-11-06T16:40:10.412Z",
  "asks": [
    {
      "pane_id": "w1:p3",
      "herdr": "esim",
      "session": "0f1e2d3c-...",
      "message": "t12ad57c7c69734480c8aaddb",
      "lines": ["Should I approve the 3 refunds over the cap?"],
      "at": "2026-11-06T16:31:39.000Z",
      "tags": ["Answer sheet · 3 questions", "+1 earlier"],
      "older": false
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `generated_at`, `as_of` | When the answer was made, and when the build that wrote the feed ran. |
| `pane_id`, `herdr` | Herdr's pane id, and the name of the Herdr session it is in. Pane ids repeat across Herdr sessions, so a client with several matches on both. |
| `session` | The conversation's id, as the page's `#s=` takes it (or its first 8 characters). |
| `message` | The asking reply's turn id, as `&m=` takes it; `null` for a turn with none, and the client then opens `#s=<session>` alone. |
| `lines` | Up to 3 plain-text lines of what is asked (each at most 200 characters): the questions of the reply's answer sheet when it opens one, else the lines of the reply that ask. |
| `at` | When the asking reply was written (ISO time). |
| `tags` | Short labels for the row, in the page's words: `Answer sheet · N questions`, `+N earlier`. May be empty. |
| `older` | `true` when the ask is more than 24 hours old at the time of the call (the feed cannot say it: it changes only when an ask does). |

The route is behind the same guard as every `/api/transcript-reader/` route (loopback Host and Origin, Fetch-Metadata, the per-start token in `x-transcript-reader-token`) and sends no CORS header; nothing is relaxed for it. It answers 404 `not_built` before the first build has written the feed or when the feed is in a format this server does not know. A client that polls it counts as an open page: the logs are watched while it polls, so an ask that is answered goes from the answer within about two seconds, and nothing is rebuilt when nobody asks. Herdr not answering gives an empty `asks` (no pane can be named). Only conversations on the reading list have an ask here: a live pane the list lacks is listed by **Sync** or by following it, as for the page.

An ask is opened in the lite page at `out/live/index.html#s=<session>&m=<message>`. The reply is scrolled to just under the header and outlined once (the 2.8-second outline fades; nothing stays lit), from a fresh load and in place, on the lite page as on the full one (`e2e/message-link-check.js` checks both, `lite.test.js` the page's rules, `api.test.js` the route).

## The embed page

For drawing a conversation that is **not** one of the reader's (Conn draws ShopBack Campus conversations, a hosted opencode workspace, in its Reader and Watch columns), a host web view (Conn's `WKWebView`) can load the reader's own transcript page and hand it the conversation's turns as JSON. The turns are drawn by the code that draws a Claude or Codex conversation (`inputBlock` and `replyCard`, with the same markdown, tables, code boxes, "N steps" rows, step sheet and styles), so markdown shows as markdown, not as `##` and `**`, and a Campus conversation looks exactly like the others. The page asks nothing of Campus or of any server and keeps nothing: Campus data arrives only through the entry point below.

```
http://localhost:8768/setup/transcript-reader/out/live/embed.html      (served: opened by a navigation, never framed)
file://<repo>/setup/transcript-reader/out/live/embed.html               (or loaded as a file; WKWebView needs read access to its folder)
```

It is the page's fourth mode (`embed`, after `local`, `hosted` and `live`; `prototype/template.html`). It holds no transcript and no token, so the file is the same bytes for the same code and a host may also copy it. A build writes it with the lite page's files (`reader.py rebuild`, or any build; `test_live.py` pins that), and the server serves it like the other pages (`api.js`, `PAGES`). It never calls the server back, whatever address it is opened from: its content policy is `default-src 'none'; connect-src 'none'; frame-src 'none'; img-src 'none'` with its own script allowed by hash, `live.js` treats the page as not served, and every read and write of `localStorage` and `sessionStorage` in it lands in memory. There is no header, search, pins or hiding, and, until the host asks for it ("The composer", below), no message bar, Reply, "Comment on this" or "Ask about this": the host has its own header, and may have its own composer. The page follows the web view's light or dark appearance (`prefers-color-scheme`).

### The entry point: `window.readerEmbed`

Installed while the page loads, so it exists when the web view's `didFinish` fires. `set` and `upsert` take an object or its JSON text and return `{ "ok": true, "blocks": <count now held>, "skipped": <blocks it could not use> }`.

| Call | Does |
|---|---|
| `readerEmbed.set(conversation)` | **Replace** the whole conversation: `{ "id"?, "live"?, "blocks": [...] }`. Idempotent and cheap to call on every change: the page keeps the nodes of every block whose content is unchanged, draws a changed block again where it stands, adds a new one and removes a gone one, so a streaming reply is one card that grows and nothing above it is touched or loses its selection. A `set` with a different `id` starts the page over; the same `id` (or none) goes on where it was. A `set` without `live` takes the working line away. |
| `readerEmbed.upsert(blocks)` | **Update or append**: `{ "blocks": [...], "live"? }` or a bare array. A block with the `id` of a held block replaces it where it stands, any other goes on the end, in the order given. `live` changes the line only when it is part of the call. Use it for one frame of the stream: send only the block that changed. |
| `readerEmbed.live(text)` | The **working strip** at the foot: "reading table-a.csv", "thinking", "writing". `""` takes it away. |
| `readerEmbed.clear()` | Empty the conversation and the strip (the `id` stays). |
| `readerEmbed.plainText()` | The conversation as plain text, in the words of `CampusTimeline.plainText()` (for the host's Copy). |
| `readerEmbed.composer(config)` | Turn the **message bar** on, with select-to-ask, Reply, comments, the batch, Send, Undo and Now (see "The composer", below). `{ "name": "Monthly review", "send": true, "reason": "" }`, or its JSON text. `composer(null)` (or `false`) turns it off. |
| `readerEmbed.sent(result)` | The host's answer to one `send` message: `{ "id": "<the send's id>", "ok": true }` or `{ "id": ..., "ok": false, "error": "why" }`. |
| `readerEmbed.composerState()` | What the bar holds, for a host that is about to reload the page: `{ "on": true, "text": "<the box>", "comments": <in the batch>, "holding": <a message is in its Undo window>, "sending": <a send waits for sent()> }`. |
| `readerEmbed.version` | `1` (the calls above that are new keep it: a host that never calls them sees the page as before). |

A call with text that is not JSON throws a `SyntaxError`, which `evaluateJavaScript`'s completion handler receives; nothing else a host sends can throw. A block of an unknown kind, an empty message and a reply with nothing in it are skipped and counted in `skipped`; a field of the wrong type is read as the empty one, as `CampusJSON` reads Campus's.

### The JSON

The shape is `CampusTimeline.blocks()` of `helm/Sources/ConnCore/Campus/CampusTimeline.swift`, field by field, so the host's side is a copy. A conversation is blocks in reading order:

```json
{
  "id": "ses_01H8X",
  "live": "reading redemptions-week-44.csv",
  "blocks": [
    { "kind": "user", "id": "msg_u1", "at": 1762500000, "text": "Can you summarise last week's voucher redemptions?" },
    { "kind": "reply", "id": "msg_r1", "at": 1762500042,
      "texts": ["## Summary\n\nSingapore grew **6%**.\n\n| Market | Change |\n|---|---|\n| SG | +6% |"],
      "tools": [
        { "tool": "read", "argument": "/workspace/redemptions-week-44.csv", "output": "market,redeemed\nSG,1204\n", "status": "ok", "detail": "12 ms" },
        { "tool": "bash", "argument": "python3 summarise.py", "output": "ERROR: no such file\n", "status": "failed", "detail": "0.3s" }
      ],
      "form": { "id": "frm_1", "status": "open", "questions": [ { "text": "Split by state?", "options": ["Yes, by state", "No"] } ] },
      "stopped": false, "streaming": false }
  ]
}
```

- **`id`** (conversation, optional): names the conversation; a `set` with another one opens it fresh, at its latest turn. Without one, every call is the same conversation.
- **Block** `kind`: `"user"` (`CampusBlock.user`) or `"reply"` (`CampusBlock.reply`; `"assistant"` is read as `"reply"`).
  - **`id`**: the item's `CampusItem.id` (a reply block's is `CampusBlock.id`, `r-<first item id>`). **Send it, and keep it stable**: it is how `upsert` finds the block and how a redraw keeps what you opened. A block without one gets one from its kind and place, which `upsert` cannot rely on.
  - **`at`** (optional): seconds since the epoch (milliseconds are read as such). `CampusItem` has none; when absent the card shows no time.
  - **user**: `text` (plain text, shown as typed, with "You" and the time).
  - **reply**: `texts` (the assistant's text parts, **markdown**, joined with a blank line as the reply; a single `text` string is read too), `tools`, `form`, `stopped`, `streaming`. The reply card has the same behavior as a Claude reply's: a reply over 90 words is clipped behind "Show full reply (N words)", and the row "N steps · edited 2 files · 1 failed" opens the list of steps. `stopped: true` adds "Stopped before it finished."; `streaming` is carried and changes nothing on screen (the strip says what the agent is doing).
- **Tool** (`CampusItem`'s tool fields): `tool` (the name; `read`, `write`, `edit`, `bash` or `shell`, `grep`, `glob`, `list`, `webfetch`, `websearch`, `task`, `skill`, `question` get their own step kind, any other is "Tool"), `argument` (the command, the file, the pattern), `output` (the text, which the step's sheet shows: a command's last 12 lines with "Show all N lines", a failed step's too), `status` (`ok`, `failed`, `running`, `aborted`: a failed step is red and counted, a running or stopped one says so in its line), `detail` (carried, not drawn). The page does not read `reasoning`, `step` or `idle` items: send what `blocks()` sends.
- **Form** (`CampusForm`): `id`, `status` (`open`, `answered`, `cancelled`), `answer` (the picked text, once answered), `questions` (`text`, `options`, `pick`). An **open** form is a reply that needs you: the "Needs you" chip, the yellow edge, and the questions in the yellow box with their options as pills. An answered one is quiet, with "Answered: ..." and the pick filled; a cancelled one says so. The page does not answer a form: the host's native controls do, then send the block again with `status: "answered"`.
- **Example:** `setup/transcript-reader/embed-fixtures/campus-conversation.json` is a whole invented conversation in this shape (two turns, tools including a failed one, a table, a code block, a long reply, an open question).

A stream is `set` once with the backfill, then `upsert` of the block each frame changed (and `live(text)`, or `upsert({ "blocks": [...], "live": "writing" })`, for the strip), or, simpler, `set` of the whole timeline on every frame: the page's redraw is per block, so the cost is the changed block's.

### The composer (opt-in)

By default the page has no way to ask anything: a host with its own composer needs nothing more. A host that wants the reader's own way of asking about a reply, in the Campus view too, calls `readerEmbed.composer({ "name": "Monthly review" })` once (after `didFinish`; again whenever the name or the reason changes, and `composer(null)` takes it away). The page then has the controls of the reader's own conversation view, drawn by the same code with the same styles, and **keeps nothing**: the box, the pointer and the batch live in the page's memory, so a reload loses them (`composerState()` says whether there is anything to lose).

- **Select text to ask about it.** Selecting words in a reply offers **Comment on this** beside the selection (Cmd+Enter on a Mac, Ctrl+Enter elsewhere does the same); a reply card has a **Reply** button (it comments on the passage selected, or on the reply); the step sheet has **Ask about this**. Each puts a pointer chip above the box: `Re your reply ("Summary Singapore grew 6%"), the part "Singapore": ...`, with "Sends exactly:" showing the whole line. A reply with no `at` has no time in the pointer.
- **Copy on select waits 0.8 s.** With the header's Copy on select on (the default; off on a phone and on the embed page), the words you select go to the clipboard 0.8 s after you let go of the mouse, not at once. Start a comment inside that time (click **Comment on this**, rest the pointer on it, or press Cmd+Enter / Ctrl+Enter) and nothing is written: the clipboard keeps what it held before, so a paste gives the earlier item, and a clipboard-history app never sees the selected line. The pointer resting on the button holds the copy; leaving without a click lets it run 0.8 s later. A new selection replaces the one waiting and starts the wait again; switching Copy on select off drops it. The wait ends early when your hands leave the page: a bare Cmd or Ctrl press shortens it to 0.25 s (the start of Cmd+Enter, and of Cmd+Tab, which the page never sees past the Cmd), any other Cmd or Ctrl key (Cmd+C, Cmd+Shift+4) copies at once, and so does the window losing focus (best effort: a page that has lost focus can be refused the write). Selecting the same passage again after a cancelled copy copies it; selecting what is already on the clipboard does not copy it twice. A comment begun after the 0.8 s finds the copy done: the page cannot take it back (reading the clipboard needs a permission, and an image or a file would be lost). On plain http (no `navigator.clipboard`) the copy stays immediate: `execCommand` needs the mouse-up's own gesture, so there is no wait to comment in. The wait needs the browser to still allow the clipboard write 0.8 s after the click: Chrome and WebKit (Safari 26's engine, the one Conn's web views use) do, WebKit up to about 3 s and not at 6 s. The decisions are in `prototype/selectcopy.js` (`deferred`, unit-tested in `selectcopy.test.js` with a clock the test moves); the browser's half is `e2e/select-copy-defer-check.js`.
- **Batch.** **Add** (or Cmd/Ctrl+Enter) puts the comment in a batch and clears the box for the next; the batch list shows each comment with **Edit** and **✕**, **Clear all** asks in the page ("Remove all 3?" and **Keep**), and **Exact text** shows what Send will type. Several comments go as one message: `3 comments:\n\n1. ...\n\n2. ...`.
- **Send, Undo, Now.** Send holds the message **in the page** for 5 seconds with the box locked (**Send** reads **Undo 5**, **Add** reads **Now**; the faded message in the conversation has Undo and **Send now**; Esc undoes, Enter sends now). Nothing has left the page until the window ends, so Undo is always "it was never sent". Then the page posts `send` to the host (above). A message that starts with a session command (`/clear`, `/exit`, `/quit`, `/compact`, `/logout`, `/rewind`) asks first in the page (**Confirm**/**Keep**); a message starting with `/` goes alone, never inside a batch, as in the reader. The message is at most 4,000 characters, as in the reader.
- **What the host does.** On `send` it types `text` into the Campus conversation, then calls `readerEmbed.sent({ id, ok: true })` (the faded message stays until a **new user block** arrives by `set` or `upsert`, whatever its text, then goes: it is the same message now drawn by the conversation) or `sent({ id, ok: false, error })` (the page says why and gives the message back: into the box when it is empty, else into the batch). A host that does not answer within 60 seconds is treated as failed, in words that say it may have gone. A host that is not listening at all (no `readerEmbed` message handler) fails at once: "No host is listening, so nothing was sent."
- **Config.** `name` (shown as `Message <name>` in the box and `To <name>` under it), `send` (`false` keeps the bar for comments, batching and Copy and turns Send off), `reason` (the sentence shown while `send` is false: "Sign in to Campus to send."). A `send: false` bar never posts.
- **No photos.** The bar has no photo button here, and a pasted or dropped picture is refused with a word.
- **Checked** by `e2e/embed-check.js`: every control above against a stand-in host that answers `sent`, in a phone width and a desktop one, light and dark, and that nothing reaches a server or a store.

### What the page does with them

- **Scrolling.** The first call, and a `set` with another `id`, opens at the latest turn, placed at the top as the reader does. Later updates follow the newest content while you are at the bottom; scrolled up, your place is kept and a **New reply ↓** button offers the way down (it goes when you reach the bottom).
- **Redraw.** Only a block whose JSON changed is drawn again. What you opened (a clipped reply, the steps list, a step) stays open across updates, keyed by the block's `id`.
- **Links.** A web address in a reply never takes the view away. If the host listens, it is told (below); otherwise a new window opens it. Only `http(s)` addresses are links (raw HTML in markdown is off and no image is fetched), as in the reader.
- **Code boxes** keep their Copy button. Selecting text does **not** copy it (the reader's Copy on select is off here).

### What the host hears

If the web view has a script message handler named `readerEmbed` (`WKUserContentController.add(_:name:)`), the page posts to it (`window.webkit.messageHandlers.readerEmbed`):

| Message | When |
|---|---|
| `{ "type": "ready", "version": 1 }` | once, when the entry point is installed |
| `{ "type": "link", "url": "https://..." }` | an `http(s)` link was clicked; the page did not navigate, the host opens it |
| `{ "type": "send", "id": "<uuid>", "conversation": "<the conversation's id, or empty>", "text": "<the exact message>", "comments": <how many numbered comments it carries, 0 for a single message> }` | the composer's message left its Undo window (or **Now** was pressed): **type `text` into the conversation exactly as it is**, then answer with `readerEmbed.sent({ id, ok })`. Only with the composer on. |

A host that does not listen needs nothing: the entry point is there when `didFinish` fires, and links open in a new window.

```swift
// the host's half, in outline
webView.loadFileURL(embedURL, allowingReadAccessTo: embedURL.deletingLastPathComponent())   // or load the served address
// after didFinish, for every change of the conversation:
let json = String(data: try JSONEncoder().encode(snapshot), encoding: .utf8)!
webView.evaluateJavaScript("window.readerEmbed.set(\(json))")   // a JSON object literal is a JavaScript object
```

Checked in a real browser by `e2e/embed-check.js` (below); the page's rules are `embed.test.js`, the build's `test_live.py`, the route's `lite.test.js`.

## A reply card names its turn

A host that lands a column on the latest finished reply (Conn's Watch focus toggle) needs the id of that reply's turn. Every reply card carries it as one attribute, on the full reader page, the lite page and the embed page alike:

```html
<div class="reply" data-turn="<turn id>" ...>
```

- **`data-turn`** is the turn's own id: the session log's record id on the full and lite pages (the same id `#s=<session>&m=<turn id>` takes, see "Links to one message"), the block's `id` on the embed page. It is on every reply card the page draws for a turn that has an id, whether or not the reply is pinned, hidden, clipped or open. A message of the captain's (`.input`) has none: the attribute names replies only.
- **The latest reply** is the last `.reply[data-turn]` in `#main`: `[...document.querySelectorAll('#main .reply[data-turn]')].pop().dataset.turn`. Cards are in conversation order, and a page that redraws one conversation (a new build, a streaming reply) keeps the same ids, so the value can be read at any time and compared with the one read before.
- **`data-msg` is unchanged**: `<turn id>:reply`, the pin's key, on the full and lite pages only (the embed page has no pins, so no `data-msg`). It stays what it was, an undocumented detail a host should leave behind: read `data-turn`.

Checked in headless Chrome by `e2e/reply-turn-check.js` (full and lite pages: every card has one, none repeated, `data-msg` is `data-turn` plus `:reply`, inputs have none, the last card is the latest reply, a fresh load names the same turns) and `e2e/embed-check.js` (the embed page's cards carry the block ids).

## Markdown files open in an editor

A markdown file can be opened in an editor from two places, and both are drawn as an element a host can find by one selector, so Conn (or any web view that hosts the reader) can open the file in its own Editor view while a plain browser still does something useful.

### The contract for a host: `.file-ref[data-path]`

In short: a link is `a.file-ref[data-path]`, the Documents view's button is `button.file-ref[data-path]`, and a click on either is a host's to take.

| Where | Element | Always carries |
|---|---|---|
| An **absolute `.md` path in a reply** (in prose, or alone in an inline-code span) | `<a class="file-ref" data-path="/abs/path.md" href="…">` | `data-path`: the absolute path, as written in the reply |
| The **Documents view** of a markdown file the reader lists | `<button class="btn file-ref" data-path="/abs/path.md" type="button">Open in editor</button>` | `data-path`: the file's absolute path on disk |

A host handles a click on `.file-ref[data-path]` anywhere in the reader page and the lite page (the full reader and Watch web views): read `element.closest('.file-ref[data-path]').dataset.path`, open that file in its editor and call `event.preventDefault()`. Nothing else is needed:

- the page looks at `event.defaultPrevented` **after** the event has gone by every listener (a zero-delay timeout), so a host listener registered before or after the page's own, in the capture or the bubble phase, has the last word; the page then does nothing more;
- the contract is only those two names and the one attribute; the link's `href`, `title` and text may change.

What counts as a path in a reply (`prototype/filerefs.js`, `filerefs.test.js`): it starts at `/` and ends in `.md`, with no `..`, `.` or empty segment; the character before the first `/` is not a word, a path or a web address (`https://x/y.md` is a web address, `~/x.md`, `docs/x.md` and `./x.md` do not say which file); a line number or anchor after it (`/a/b.md:12`, `#top`) is not part of it, and `plan.md.bak` or `plan.mdx` is another name. Prose, and an inline-code span that is the path and nothing else, link; a command that holds a path (`` `cat /a/b.md` ``) and a fenced code block do not. Only replies link (a message from you or Firstmate is not touched, and neither is a markdown file's own text in the Documents view). The embed page links nothing: a Campus conversation has no files here.

### With no host (a plain browser)

- **A link** keeps the reader's own behaviour: a file the reader lists as a document opens in the Documents view (the link's `href` is that address, `#s=<session>&d=<document>`, followed in place) and any other path opens in VS Code (`vscode://file/<path>`). The hosted copy links only the documents it holds, since it is not on the machine the paths are on.
- **The button** opens `vscode://file/<path>` (each segment encoded). It is on the served page only, for a markdown file with a path (never a sketch or a picture, which are not text to edit).

Checked in headless Chrome by `e2e/file-ref-check.js` (which paths link and which do not; the host's `preventDefault` gets each path and nothing moves; a listed file opens in the Documents view; the button's `vscode://file/<path>` is caught by the Navigation API before it leaves the page, so no editor starts; no button on a page; the lite page draws the same links). Design: DESIGN.md, "Markdown files open in an editor".

## The hosted copy

The way towards reading the transcripts from a phone while the laptop is off (the hosted reader plan, ships 1 and 2).

**Nothing is hosted.** Everything below runs on this laptop and writes only to `out/`: no cloud account, bucket, domain or upload exists, and no code here talks to one. Hosting it (ship 3) waits for a written ShopBack security or IT exemption for keeping these transcripts on a personal Cloudflare account, or else for the in-policy alternative, an app in ShopBack's Replit workspace (plan sections 5 and 6).

```bash
python3 setup/transcript-reader/sync.py --build-only                 # every fleet session
python3 setup/transcript-reader/sync.py --build-only --reading-list  # the local reader's list, to compare the two pages
```

It writes `out/hosted/`: the shell page `index.html`, `index.json` (the conversation list), one object per conversation, per named document and per week of fleet records, and a manifest. A run builds a conversation again when one of its logs changed, when the reader's own rules changed (a fix to the parser, say), or when a steering inbox or task-instruction file it shows changed; it rewrites an object only when its content changed. `--full` builds everything again. Its help (`--help`) lists the files and the scope. The reader's server serves the shell beside the local page: `http://localhost:8768/setup/transcript-reader/out/hosted/index.html`.

The shell is the same page as the local reader, loading `index.json` and then one conversation, document or week at a time, so it shows the same conversations, turns, replies, steering messages, documents and fleet timeline. It differs only where a copy without the laptop must:

- **No Follow, Reopen or Close; Send goes through a queue.** Nothing here changes the reading list. The message bar, Reply, "Comment on this", "Message about this file" and the batch are the local page's own, but Send does not reach Herdr: it queues the message for the laptop (see "Send" below), and it takes no photos (see "Photos in a message" above). The answer sheet (`sheet.html`, opened from "Answer sheet →" and each "Answer these questions →") is the local one: the same cards from a grill-me reply, the same one-line keyed answer (`A1=accept;A2=inline`), with Copy and a Send that queues the same line.
- **Says how old it is.** A line under the title says "As of 14:02", the time the laptop built it, and turns into "Laptop asleep or not syncing since 14:02" once that is over 10 minutes old. When the laptop's own server answered that read, an old copy is not a sleeping laptop, and the line says what is true: "Copy from 14:02: nothing has built a newer one. Sync builds one." **Sync** has the laptop build a new copy (see "What builds the copy" above) and then takes it.
- **Herdr as of the build.** The picker shows each agent's state as Herdr reported it at the build, with "at last sync" so the phone never claims the pane is live now. The line under the controls keeps the build time ("Working at 14:02") and says that Herdr states are as of then.
- **The same live sections and names.** The picker puts starred sessions first, then the unstarred live sessions in the same newest-first order and with the same Herdr labels as the live page. A starred closed session stays in the Starred group without a live label. The default live-plus-starred copy has no other closed sessions to crowd the list. An explicit `--panes all` build keeps its existing Closed panes group.
- **Slower refresh.** Every 30 seconds while the page is visible it reads `index.json` again and swaps in a conversation whose stamp changed, where you are reading. New page code reloads it.

### Send, through a queue (local only)

The hosted page cannot reach Herdr, so Send is a request the laptop carries out when it is awake (plan section 8). All of it is local: no network, and every test and lab run uses a fake Herdr.

1. **The page queues it.** Send writes a request, `{id, session_id, text, at}`, through the reader's own server (`POST /api/transcript-reader/queue`, behind the same guard and token as Send) into `q/<uuid>.json` in the copy's folder. A sealed copy's page gzips and seals the request itself, under the key it holds and with its own path bound in, so the server stores `q/<uuid>.json.enc` bytes it cannot read. Nothing is sent to Herdr, and the bar says "Queued for <pane> at 14:05. The laptop sends it when it is awake." The faded message in the conversation reads "Queued … waiting for the laptop to send it".
2. **The sync sends it.** Every `sync.py` run (`--build-only`, which drains `out/hosted/`, or `--seal`, which drains that and the bucket) first runs `drain.js` on each folder that has a request waiting. For each one it asks the local reader's own send (`api.js` `sendPrompt`, the same code as the local Send) whether the session is a conversation of this copy, whether one live Herdr pane runs it, whether that pane's agent is Claude running that very session in the foreground (not suspended to a shell) and not at a permission prompt or question; then it empties the pane's input box and sends the text as one message. Nothing starts when no request waits.
3. **A receipt comes back.** `r/<uuid>.json` (sealed: `.json.enc`) says `sent` with the pane's name, or `refused` with the reason in the same words the local Send uses. The page asks for it every 4 seconds while one is waiting, and shows "Sent by the laptop at 14:06 · waiting for <pane>" or "Not sent · <reason>" with Dismiss. A reload keeps the queued messages of that tab.

4. **Undo.** `POST /api/transcript-reader/unqueue` (`{copy, id}`) takes a waiting request back. The drain takes a request by renaming `q/<id>.json(.enc)` to `q/<id>.json(.enc).claimed` before it reads it, and unqueue renames the same file to an empty tombstone `q/.cancelled-<id>`; a rename is atomic, so exactly one of them has the message. `cancelled` means no drain will ever send it (a message this server never had gets a tombstone too, and a late post of the same id is refused with 409 `cancelled`); `too_late` means the drain has it, and nothing is changed. A sealed request is never opened, only renamed. Tombstones are forgotten after two days. A relay that has no such route (the Replit app, not deployed yet) makes Undo say so, and the message is still sent.

Rules the drain keeps: a refusal is final (nothing retries by itself; you send again); a request whose own time, sealed inside it, is over 12 hours old is refused as expired, and one dated more than 10 minutes ahead (a wrong clock on the device) is refused; a request is never sent twice (a "sending" receipt is written first, a run that stopped midway turns it into "refused: interrupted", and the ids handled are also kept on the laptop only, in `out/`, for as long as a copy could still be fresh); a sealed bucket takes only requests sealed under its key and a plain copy only plain ones, as the caller says and never as the folder looks; receipts older than a week go; at most 50 requests wait. Wipe takes `q/` and `r/` with the rest.

```bash
python3 setup/transcript-reader/sync.py --build-only      # drains out/hosted/q
HOSTED_READER_PASSPHRASE=... python3 setup/transcript-reader/sync.py --seal   # drains it and out/bucket/q
HOSTED_READER_PASSPHRASE=... node setup/transcript-reader/drain.js out/bucket --sealed   # or just the drain
```

`HOSTED_READER_HERDR` names the Herdr binary (default `herdr` on PATH); the printed LaunchAgent carries the folders of `node`, `python3` and `herdr`. To try it without touching a real pane, point that variable at a script that records its arguments (the tests do).

### The sealed copy (`--seal`)

`--seal` is the sync agent of ship 2 with its one target, a local folder (`out/bucket/` by default) laid out as the bucket would be. Each run builds as above, then takes the conversations active in the last 90 days, the documents they name and the fleet weeks of the last 90 days, and:

- **Redacts.** Every text in every object goes through `redact.py`: AWS keys, `sk-` API keys, GitHub, GitLab and Slack tokens, JWTs, bearer tokens, private keys (also one cut off before its END line), passwords and secrets in URLs, any secret given a value (`PASSWORD=...`, `db_password = ...`, `"token": "..."`, `old token=... is dead`; a name like `TOKEN_HEADER`, a `$reference` or a placeholder stays), and 64-hex tokens become `[redacted:<kind>]`. It looks for secrets, not personal data. The counts, never the text, go to `out/hosted/redactions.json`. The laptop's own copy keeps the original.
- **Encrypts.** Each object is gzipped and sealed with AES-256-GCM under a key derived from your passphrase (PBKDF2-SHA256, 600,000 rounds; the salt is in `k/params.json`, which holds no secret), its own path bound in, so the host could neither read one nor pass one off as another. The page opens them in the browser.
- **Writes only what changed**, deletes what fell out of the 90 days, and seals the index again at least every 5 minutes, so the "As of" line stays fresh while the laptop is awake.

```bash
export HOSTED_READER_PASSPHRASE='YOUR_PASSPHRASE_HERE'   # or leave it unset to be asked in the terminal
python3 setup/transcript-reader/sync.py --seal
python3 setup/transcript-reader/sync.py --wipe                  # empty out/bucket/ of what --seal wrote
python3 setup/transcript-reader/sync.py --launch-agent          # print a LaunchAgent that runs --seal every minute
```

The passphrase is read from the environment, from the login keychain (only when there is no terminal: the LaunchAgent, or the reader's server answering the page's Sync), or from the terminal, and never written or printed. A passphrase the bucket does not know stops the run; `--new-passphrase` seals everything again under it (losing the passphrase loses nothing). The LaunchAgent is only printed, to install yourself if you want it: it reads the passphrase from your login keychain at each run (`security add-generic-password -s pmos-hosted-reader -a "$USER" -w` stores it, asking for it), and it runs while the Mac is awake.

**Install the LaunchAgent** (yours to do, once; run it from the checkout the agent should run from, because the plist names that checkout's `sync.py`, and keep that checkout on the branch you want it to run):

```bash
security add-generic-password -s pmos-hosted-reader -a "$USER" -w     # once: asks for the passphrase the copy is sealed under (add -U to change it)
python3 setup/transcript-reader/sync.py --launch-agent > ~/Library/LaunchAgents/com.pmos.transcript-reader-sync.plist
plutil -lint ~/Library/LaunchAgents/com.pmos.transcript-reader-sync.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.pmos.transcript-reader-sync.plist    # runs at once, then every 60 seconds
```

Check it: `launchctl print gui/$(id -u)/com.pmos.transcript-reader-sync` (its state and `last exit code = 0`), `tail setup/transcript-reader/out/sync-agent.log` (one "Sealed copy in ..." line per run; the file only grows, about 1 MB a day), and `ls -l setup/transcript-reader/out/bucket/index.json.enc` (never more than about 5 minutes old while the Mac is awake). Remove it: `launchctl bootout gui/$(id -u)/com.pmos.transcript-reader-sync`, then move the plist out of `~/Library/LaunchAgents`. The plist's PATH holds the folders `node` and `python3` resolved to when it was printed (a Homebrew `Cellar/<version>` folder), so print it again after `brew upgrade node` or `python`.

| Run | Wall | CPU | Peak memory |
|---|---|---|---|
| First full seal (once) | 127 s | 116 s | 239 MB (Node 8.5 s, 239 MB) |
| A minute with nothing changed | 1.2 s | 1.0 s | 67 MB |
| The 5-minute heartbeat (the index sealed again) | 1.5 s | 1.2 s (Node 0.2 s) | 66 MB |
| A minute in which one conversation changed | 4.6 to 4.9 s | 3.5 s | 132 MB |

Quiet, that is about 1 CPU-minute an hour (under 2% of one core); with a conversation changing every minute, about 3.5 CPU-minutes an hour (6% of one core). The process ends after each run, so no memory stays held, nothing goes over the network, and a busy minute writes about 1 MB (the index, in plain and sealed form, and the changed object). It does not wake the Mac: launchd misses an interval that falls while the Mac sleeps (`man launchd.plist`, StartInterval), a run holds no power assertion, and the copy simply stops being refreshed until the Mac is awake again.

To review it locally, start the reader's server and open the sealed copy beside the local page: `bash setup/transcript-reader/serve.sh start`, then `http://localhost:8768/setup/transcript-reader/out/bucket/index.html`. It asks for the passphrase once; "Remember on this device" (on by default) keeps the derived key, never the passphrase, in this browser until "Forget this device".

## What it touches

- Reads Claude Code session logs (`~/.claude/projects` and the `projects/` of each other Claude config folder, see "Claude under another config folder"; or only the folder `PMOS_READER_PROJECTS` names, for a test or a measurement that must not touch the real ones) and its running-process records (`sessions/` of each), the fleet homes' records, Herdr's session list and snapshots, and the markdown files messages and replies name. It lists the HTML files and the image files they name (`out/html-files.json` and `out/image-files.json`, paths only, never served) and the server reads one only when you open it.
- Writes `out/` (photos you attach to a message are saved in `out/uploads/`, owner-only, and never served; and, when a rebuild is asked for by the server, runs one `reader.py worker` that stays running while pages are open), the passcode hash (`out/passcode.json`, only on `serve.sh passcode`), the pins file (`~/.config/pmos-transcript-reader/pins.json`, only on a pin or an unpin; it holds which messages are pinned, not their text) and the stars file (`~/.config/pmos-transcript-reader/stars.json`, only on a star or an unstar; it holds which conversations are starred). `out/` is gitignored: the pages embed private transcripts. Like Claude's own logs, `out/` and everything in it is the owner's alone (folders 0700, files 0600), and each rebuild narrows any file an earlier version left readable by others. That includes `out/parsed/`, each log's turns as last parsed: a rebuild parses again only the logs that changed since (or all of them once the parser changes), and removes a parsed log no build has used for a week. A rebuild started by hand while the server runs its own waits for it to finish.
- Sends a prompt to one Herdr pane, only on a Send click (or, for the hosted copy's Send, when `drain.js` carries out a queued request), and only to the one live pane whose agent runs that listed session. It refuses an agent waiting at a permission prompt. It never starts, stops or closes a Herdr session, tab or pane, and never addresses the default Herdr session. Undo only renames or empties files in a copy's `q/` folder (the `unqueue` route); it sends nothing to a pane.

The server routes are in `api.js`: the pages under `out/` (the hosted shell and its objects in `out/hosted/` and `out/bucket/` too, and the lite page and its objects in `out/live/`) and `/api/transcript-reader/*` use the Herdr organizer's guard (exact Host and Origin, Fetch-Metadata, a per-start token) and send no CORS header, so another website cannot read the transcripts or send a prompt.
The reader's server serves nothing else, and `setup/serve.sh` refuses any request into the reader's `out/` folder, so no other app shares the pages' origin. Still, no endpoint hands out the token.
The server writes it into a page only when a browser tab opens that page, and the page refuses frames and cuts off whoever opened it.
A restarted server has a new token: an open page reloads itself once to pick it up (not while you are typing).
A path that the file system resolves into `out/` (another letter case, Unicode form or a symlink) is answered by `api.js` on the reader's server, and refused with a 404 by `setup/serve.sh`.

## When the page stops updating

The footer then says "Not syncing since <time>: The rebuild took over a minute and was stopped." That means a rebuild froze, and the server ended it and tried again 30 seconds later with the same result. The cause found so far is a file that cannot be opened: a markdown file a reply names, in `~/Downloads` or `~/Desktop`, which macOS holds behind a permission dialog for the app the reader runs under (Conn, say) until someone answers it, and a cloud folder whose app is not running does the same. Every process that opens a file there waits, the reader's build included (try `ls ~/Downloads` in a terminal under the same app: if it never returns, that is it). Answer the dialog ("<app> would like to access files in your Downloads folder", Allow), or run `tccutil reset SystemPolicyDownloadsFolder <app's bundle id>` (and `SystemPolicyDesktopFolder`) to have macOS ask again.

The reader no longer waits for such a file. A named markdown file is read by a helper thread that is given 3 seconds (`prototype/bounded_read.py`); one that does not answer is left out of the page's documents, like a file that cannot be read, and its folder (all of `~/Downloads`, `~/Desktop` or `~/Documents` when the file is under one of them) is not asked again for 5 minutes, when the build reads it again. A markdown file opened from the page (`md-open`) has 5 seconds and the same 5 minutes of rest, and answers 504 "That folder is not answering" instead of freezing the server. Checked by `e2e/sync-hang-check.js` (below).

## Speed from a log write to the page

A new reply shows on the page about **1.5 seconds** after the agent writes it, on the owner's own data (66 listed sessions, a 17.6 MB page), where it took 7 to 25 seconds before (median 15). Three things got it there; each stage's numbers are in DESIGN.md, "Quick replies".

- **The server notices the write.** While a page is open (it polls, or waits on `events`), the server watches the folders holding the listed logs (`fs.watch`, with a half-second sweep underneath for a notice the file system misses) and starts the rebuild when a listed log is newer than the page. It no longer waits for the page's next poll, and the 3-second pause between rebuilds is a quarter second. A session that writes every second would otherwise be rebuilt for every second, and each build's page is published and read again by every open page, so rebuilds that logs changing start begin at least 2 seconds apart: the first write after a quiet spell is rebuilt for at once, and the writes within the 2 seconds after it are rebuilt for together when they are over (`REBUILD_EVERY_MS` in `api.js`). A new reply is on the page within about 2 seconds of being written, however busy the logs are. With no page open it watches nothing and rebuilds nothing, as before.
- **The rebuild is one second, not fifteen.** `reader.py worker` is a `reader.py` that stays running, started by the server on the first rebuild and ended after ten minutes idle (or after 500 requests, or when `reader.py` or a builder changes on disk): the page, the answer sheet and the checks for closed panes run in that one interpreter, and what one build learned about the folders, log heads, chains, file names and answer sheets the next one uses. If the worker cannot take a request (it did not start, it died), that request runs in a fresh `reader.py` the way it always did. A rebuild started by hand (`reader.py add`, `rebuild`, ...) is the same code, started cold in its own interpreters: about 6 seconds on the same data where it took 15 to 20, because the search for each conversation's `/clear` chain looks at the logs written near the moment of a clear instead of asking every log, and reader.py asks for each chain once instead of twice.
- **A rebuild costs what changed.** The worker keeps each conversation's finished result between builds (`prototype/build_cache.py`): its turns as JSON, the documents it names and the little the page needs to place it. A result is used again while its logs, its home and every file system answer its build was given still hold. Those answers are recorded when the build first asks for them (a document a reply names, a steering message, a backlog, a path that was not there, a folder's listing) and looked at again before the result is used, so a file that appears, goes or changes rebuilds exactly the conversations that asked about it, and nothing else; the folders' task files are kept the same way. The Herdr panes, the order of the conversations and the pieces of the page between them are worked out for every build, from small records. The page, its stamp, the file lists and the tool output are the same bytes a build from nothing makes (`test_cache.py` holds the two to each other after every kind of change and after random runs of them). A page that would differ from the one already written only in its build time is not written again, and nor is an answer sheet that no sheet changed, so an open page is not told of a build that shows nothing new. A rebuild asks Herdr once (it asked three times) and asks for each chain's clear once. On the owner's 75 listed sessions a rebuild with one conversation changed takes about 0.1 to 0.3 seconds of CPU where it took about 2, and the worker's memory stays near 250 MB where a build from nothing peaked near 900 MB (DESIGN.md, "Worker cost").
- **The page is told at once.** An open page keeps one request waiting on `GET /api/transcript-reader/events?reader=<build>&wait=25000`, which the server answers the moment a newer build is published, or after 25 seconds with nothing new (then the page asks again). That is one small request in 25 seconds where the 2-second tick made twelve, nothing is downloaded until a build exists (then the usual small delta), and a hidden page does not wait. The tick stays: it carries the Herdr states, and it still sees every build, so a server without the route (an older one) works as before.

On the phone over Tailscale the same path applies, and the wait is one request, so a quiet reader costs the relay nothing it did not already cost. The phone's page needs no change besides the new page code, which it takes as it takes any: by reloading when the server's page template changes.

The server compresses its text and JSON answers (`compress.js`: brotli or gzip, whichever the browser accepts), on loopback and both tailnet listeners. ## Typed asks (S3, behind a flag that is off by default)

A leader that sends the captain keyed cards (`Z1`, `Z2`) can write one **typed record** first with Firstmate's `bin/fm-captain-ask.sh` (its header owns the grammar, the schema `fm-ask.v1` and the lifecycle; `docs/captain-asks.md` in Firstmate is the overview). The reader reads those records and shows them where it showed the prose cards, so an ask no longer rests on guessing from the reply's wording. Records are additive: the prose cards stay, and with the flag off nothing below happens.

**Switches** (the environment of the server and the worker, like `PMOS_READER_FLEET_TIMELINE`):

| Variable | What it does |
| --- | --- |
| `PMOS_READER_TYPED_ASKS` | `1`, `on`, `true` or `yes` turns typed rendering on: typed sheets, the Typed ask chip, the typed counts and the WAKE_ACK fold below. Unset or anything else: the pages, the counts and the folds are what they were (the 171 frozen sheets in `answer-sheet-fixtures/` hold the sheet side to that). |
| `PMOS_READER_TYPED_PROSE_OFF` | Comma-separated home ids (`main`, `secondmate-esim`). A listed home no longer counts prose-only asks in "needs you" (they read "Asked"). Empty by default, and read only while the flag above is on. The coverage table's gate and the captain's word turn it on; nothing here does. |
| `PMOS_READER_TYPED_HOMES` | Colon-separated extra homes to look for records in (a lab's). Normally a conversation's own home and the home that dispatched it are enough. |

**Where the code is.** `prototype/typed_lines.py` finds the in-band lines in a finished turn (`ASK_RECORD v1 <id> ... sha=<12 hex>`, `ASK_ANSWERED v1 <id> ...`, `WAKE_ACK: nothing-new|news through=<N>`, the reply's `ask: <id>` footer); the parsed-log cache depends on it, so it holds nothing else. `prototype/typed_asks.py` is everything that reads records, with no page code in it: loading across homes, the state derivation, the checks, the backlog gates, the questionnaire mapping, the annotation of a conversation's turns. `prototype/typed_coverage.py` is the coverage job. The builders call them from four places (`finish_exchange`, `thread_session`, `mark_sheets`, `session_sheet`) and `build_questionnaire.py` lays the typed sheets over the prose ones.

**How a record becomes a sheet.** For each turn whose tool output ends in an `ASK_RECORD` line, the reader finds the record (`<home>/state/ask-records/<id>.json` and `.events`) in the conversation's home or the home that dispatched it, and checks three things: the record was **linked** (the id and sha were printed in that turn), **unmodified** (the file's sha-256 prefix is the printed one and the one its `opened` event holds), and **written by this conversation** (the writer session it claims is one of the conversation's sessions: a `/clear` changes the id, so the whole chain counts). A record that fails one is shown as prose only and counted as such. A record that passes becomes the turn's sheet: its cards, in the questionnaire dict the sheet page already takes (`typed_asks.sheet_from_summary`), with the prose parse of the same reply lending only the title and the text above the cards. A typed ask the prose finder cannot read still gets a sheet.

**What the sheet adds.** A provenance row (who wrote it, in which home, which session and task, when, the record's sha, the three checks); each card's gate beside the backlog's own hold reason (the reader reads the home's markdown backlog read-only: `Backlog: <task> - held for you in the backlog`, with the hold reason under it); "Not asked any more" for cards that are withdrawn, replaced by a later ask, expired, **stale** (the task was held again since the card was asked, so it is a different call) or **closed elsewhere** (the task is no longer held for you); and, for a card you answered in chat that the record has not been told about, "You answered Z1 in chat. The record has not been told." On the reader page the reply wears a **Typed ask** chip (the tooltip names the record and its open cards) and its box lists the record's cards, whether or not the reply repeats them.

**Counts ("needs you").** A turn with a passing record is open while a card is still to answer (the record's cards, minus the ones you answered in chat), settled once every card is answered ("Answered", or "Answered in chat" when the record was not told), and quiet when what is left will not be asked. A typed ask the prose finder missed becomes a needs-you turn. Every turn that needs you without a passing record is a prose-only ask and counts as ever, unless its home is in `PMOS_READER_TYPED_PROSE_OFF`. **Answered in chat** is `Z1=value` in a later message of yours (a key with no value or a placeholder such as `Z1=...` answers nothing; a later turn that opens another ask with the same key takes the key from then on). **Record lag** is a card answered in chat whose record was still not told an hour later: it is shown on the sheet and counted per home.

**The wake marker.** A wake-up turn whose ack call printed `WAKE_ACK: nothing-new` folds, even when the prose finder saw an ask in it (that ask was made in an earlier turn; this one restates it, so it stops counting); `WAKE_ACK: news` keeps it open; a turn that opened or answered an ask, or whose reply is an API error, never folds on the marker. A turn with no marker (an older Firstmate, a drain that could not say) keeps the rule it had. The turns the parser keeps open on purpose (the newest, the answer to your own message) stay open.

**Coverage and the per-home table.**

```
python3 setup/transcript-reader/reader.py typed-coverage                 # the table; writes out/typed-ask-coverage.json
python3 setup/transcript-reader/reader.py typed-coverage --json
python3 setup/transcript-reader/reader.py typed-coverage adjudicate <record id> <leader-miss|detector-miss|false-positive>
```

Per home, over 14 days: **typed** (turns with a passing record), **prose-only** (turns whose reply makes a keyed sheet and carry no passing record), **coverage** (typed over both), **agreement** (of the turns that have both, the share with the same card keys; each other one is a disagreement to adjudicate), **detector-miss** (typed turns the finder made no sheet of), **unlinked** (records a home holds that no listed conversation names), **record-lag**, and **marker** (ack calls whose output carried a `WAKE_ACK` line, over all ack calls). The gate is `eligible` only when, for each of the last 14 days, the window up to that day held at least 10 asks at 80% or more, every disagreement is adjudicated and nothing is unlinked; it switches nothing on. Adjudications are kept in `~/.config/pmos-transcript-reader/typed-adjudications.json` (or `PMOS_READER_TYPED_ADJUDICATIONS`). It reads the logs, the records and the backlog, and writes only `out/typed-ask-coverage.json`.

**Known limits.** The reader rebuilds when a listed log changes, so a record or a backlog that changes on its own (a task closed elsewhere) shows at the next rebuild (any change of a listed log, Sync); the leader's own `open` and `answered` calls are log changes, so those show at once. One reply that opens two records shows the first. `unlinked` only knows the conversations on the reading list. The hosted copy and the offline phone copy never carry typed content (their builders do not take the typed overlay), because the hold reasons are the backlog's text.

**Shared parser fixtures.** `typed-ask-fixtures/keyed-replies.json` holds the replies whose `KEY=value` answers every reader of them must find alike: the three in this folder (`typed_asks.keyed_answers`, `build_prototype.answered_keys`, `build_questionnaire.sent_answers`) and Firstmate's `reply` mode of `bin/fm-captain-ask.jq` (run by `test_keyed_replies.py` when jq and the Firstmate checkout, `PMOS_READER_FIRSTMATE` or `~/workspace/firstmate`, are on the machine). The differences that are on purpose (a placeholder, a long value) are in the file with the reason, so a drift on either side fails a test.

**Frozen sheets.** `freeze_sheets.py` wrote every reply of the reading list that makes an answer sheet, with the sheet the parser made of it, into `answer-sheet-fixtures/frozen/` (private text, gitignored) and a digest-only `frozen-manifest.json` (tracked). `test_frozen_sheets.py` checks them all when the folder is there, and the manifest alone when it is not. After a parser change that was meant to change sheets, `freeze_sheets.py --refresh` recomputes the expectations of the replies already frozen (copy the folder aside first and read the difference; refreshed once, 2026-11-10, for review groups and table-cell choices).
