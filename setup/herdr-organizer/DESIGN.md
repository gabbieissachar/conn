# Herdr restart tools - design note

Status: decided in the step 1 brainstorm (2026-10-04). Built on branch `fm/herdr-organizer-app-tools`.
App: `apps/wip-herdr-workspace-organizer.html`, served by `setup/serve.sh`.

## Purpose and flow

One browser page to run and understand the safe computer-restart flow for named Herdr sessions.
The user is the person restarting their own machine; the page is a local cockpit, not a remote console.

1. Inspect sessions (default session never selectable).
2. Verify identities per pane; apply the verified rows.
3. Resolve the panes that stay manual (manual identity form).
4. Run the prepare preflight; acknowledge only intended failures; seal a bundle.
5. Restart the computer (checklist item only).
6. After boot: attach each bundled session in a terminal, run the reconcile preview, copy the confirm command and run it in a terminal.

The page also produces a redacted report of the verify and preflight results for sharing.

## Decisions

| # | Decision | Chosen |
|---|---|---|
| 1 | What the page executes itself | Tier 0, tier 1 and the two rollover tiers 1s and 1p (below). Tier 2 and 3 are copy-only. |
| 2 | Manual identity, folder mismatch | Refuse unless the explicit "folder differs, I confirm" override is sent; the server re-checks it. |
| 3 | Share report labels | Workspace, tab and session names masked by default (`Workspace 1`, `Tab 3`, `Session A`); a per-report toggle adds real names. Pane ids always stay. |
| 4 | Default session scope | All running non-default sessions selected. Unticked running sessions get a visible warning. The server always receives an explicit list. |
| 5 | v1 scope | Core plus per-item preflight acknowledgements. Manual identity is paste-an-id only. |
| 6 | Clean up empty tabs in every workspace (asked for mid-build) | A card in the Workspaces view. The page runs the read-only preview for every workspace and copies the exact commands. Closing tabs is copy-only. |

The page never runs `herdr-organizer archive`, `archive-all --execute`, restore, `restore-batch --execute`, and it never types into a pane. From tier 1s on (not built yet) it may arm firstmate's own roller by creating a switch file, and the roller then stops and restarts fleet sessions later by firstmate's own gated procedure. Until A2 is built the page writes no rollover file at all.

### Rollover switches (2026-10-26, slice A1)

`rollover-state` is tier 0: it reads, for every home in the server's registry, the five switch files in `<home>/config` (`rollover-live`, `rollover-crew-live`, `rollover-off`, `rollover-primary-live`, `rollover-primary-off`), the home's watcher lock, the task records it could name in a switch, and one mtime (`state/rollover/log`). It writes nothing, reads no log text, and sends no path, process identity, lock folder name or file content: only the home's label and id, a state word per file, a count of listed ids, firstmate's own sentence for what each kind will do, and the task ids with the reason each one could not roll now.
- The registry is `HERDR_ORGANIZER_ROLLOVER_HOMES` (`label=/abs/path` entries; default: the one gauge home). The server refuses to start on a bad entry, a repeated label or a repeated home. The browser names a home only by its id (`h` plus eight hex characters of the realpath's sha256).
- A home is read only while it is still the registered realpath, a real directory with real `state/` and `data/` folders, and a firstmate home (`state/.lock-session` or `.fm-secondmate-home`). Otherwise its status says why and nothing else of it is read.
- A watcher counts as running only when firstmate's own `fm_watcher_healthy` checks hold: a lock that is a link to a `.watch.lock.owner.*` folder directly under `state/`; a live pid; the lock's `fm-home` resolving to the registered home (it holds the raw `$FM_HOME`, so spelling is compared by realpath); `watcher-path` a regular `bin/fm-watch.sh`; the lock's process identity equal to the one the server recomputes with the same `ps` call (macOS only; elsewhere `identity_unverifiable`); and a beat younger than 300 s. Each failure has its own name: `no_lock`, `unsafe_lock`, `stale_pid`, `other_home`, `identity_mismatch`, `identity_unverifiable`, `beat_old`.
- The code that reads a switch is the code the home's watcher runs, found only through that lock, so a home with no running watcher shows no effective sentence. Whether that code reads a given switch is a text check of its `fm-rollover.sh` (`read` or `not_read`). The roller is started afresh on every watcher pass, so the file on disk is what the next pass runs; no comparison with the watcher's start is made.
- A home that is registered but whose watcher does not run cannot be armed (A2 will refuse it); Stop and Undo will still work there.
- The same module is the only one that will write a switch file in later slices, one home at a time.

## Cross-site protection

`setup/serve.sh` sends `Access-Control-Allow-Origin: *` on every response and its listener had no host argument (it bound all interfaces).
Any web page the user visits could otherwise call a write endpoint on localhost.
Every `/api/herdr-organizer/*` request therefore passes these checks, all covered by tests:

- The listener binds to loopback only (`127.0.0.1` and `::1`). This changes the whole server, not just these routes.
- The Host header must be one of `localhost`, `127.0.0.1`, `[::1]` on the served port (defeats DNS rebinding).
- `Origin` is required on POST and must equal the served origin exactly (scheme, host and port). On GET it may be absent (same-origin) but must match when present.
- `Sec-Fetch-Site`, when sent, must be `same-origin` or `none`.
- A per-server-start random token (32 random bytes) is handed out by `GET /api/herdr-organizer/token` and must come back in the `X-Herdr-Organizer-Token` header on every other call, compared in constant time. The custom header forces a CORS preflight for any cross-site caller.
- POST bodies must be `application/json`.
- These routes are dispatched before the shared CORS and OPTIONS handler and never send `Access-Control-Allow-*` headers. A preflight to them is answered 403.
- Only one tier 1 action runs at a time (409 otherwise); child processes have timeouts and bounded output.
- Child processes never inherit `HERDR_SESSION`, `HERDR_PANE_ID` and the other Herdr context variables from the shell that started the server. `register` prefers the current pane over explicit pane arguments, so an inherited pane id would register the wrong pane.

The older `POST /api/herdr-workspace-organizer/snapshot` stays untouched (fixed command, no input).

## Fixed-action allowlist

One dispatcher, `POST /api/herdr-organizer/run`, body `{action, params}`.
The browser names an action and sends validated parameters; it never sends a command, an argument list or free text that reaches a shell.
Commands are spawned with argument arrays (never a shell) and fixed argument shapes.

Validation:

- Session name: must appear in `herdr session list --json` output, be running, not be `default`, and not start with `-` (a stopped session on this machine is literally named `-h`).
- Pane, workspace and tab ids: match `^w[A-Za-z0-9]+(:[pt][A-Za-z0-9]+)?$` and exist in the live pane list of the named session.
- Bundle id: pattern plus presence in the bundle list. A bundle is only eligible after every member of its manifest is validated against the live `herdr session list`: it must name at least one session, every member must be a well-formed, distinct session name, none may be the default session, and Herdr must know every member. A member that is merely stopped stays eligible but must be attached before the preview runs. The preview repeats this validation immediately before it starts the tool, so a bundle made outside the page cannot reintroduce the default session. Every component of a bundle (the state folders, the bundle folder, `manifest.json`, the `ready` marker and the journal file) must be a real directory or a regular file; a link is refused and never read through.
- Pane write path: one strict validator for a manual identity save. The pane must be listed exactly once; its workspace, tab and pane ids must be well formed and belong to the same workspace; its folder must be present, absolute, canonical (no `.`, `..`, doubled or trailing slashes), free of control characters, and an existing directory. The folder is resolved to its real path, and the store check and the registry write both use the normalized values, never the raw pane list. A pane that fails stops the save before the store check or the registry starts.
- Acknowledgements: accepted only when the exact `session|workspace|tab|pane` (or `session|workspace`) identity appears in the latest preflight failure list. No free text, no global bypass.
- Unknown params and unknown actions are rejected.

Copy-only commands are also built on the server, from validated values only, so a pasted command can never carry unvalidated text.

## Manual identity

Panes offered: only panes the verifier did not verify. A manual save cannot overwrite a verified identity.
Checks, cheapest first:

1. Format: UUID shape for the chosen client.
2. Exists in the real client store (Claude project files; Codex session index and rollouts), via the verifier's own `ClaudeStore` and `CodexStore` classes in a read-only helper.
3. The store's recorded folder equals the pane's current folder, otherwise refused unless the override is sent. A store that records no folder for that session cannot be matched either, so it needs the same override (with its own message).
4. Not already registered to another pane (hard refusal; the page shows a copy-only remove command).

Each save also requires a confirm token naming the pane, a pane whose client matches the pane's detected agent, and no identity check: the id is saved on the layers above alone. A check from the last hour still adds protection: a pane it proved verified is never overwritten, and a pane it found unverified may be replaced freely. Without that knowledge, a pane that already holds a different registered session is refused with `pane_registered` unless the request carries `replace_existing` (the form's "I confirm replacing it" box). The folder override does not stand in for that confirmation, and neither bypasses layer 4.

Layer 3 is the independent cross-check: a check that only proves an id exists cannot prove it is the right one.
The id travels browser to server in a JSON body, then to `agent-session-registry.py register --allow-no-herdr` as one short-lived process, and is never logged or echoed.
Afterwards the page shows only the first 4 and last 4 characters.
Because `register` only takes `--session-id` on its command line, the id is visible to same-user `ps` for the life of that process (see companion tasks).

## Independent review follow-ups

An independent review of this branch confirmed the HTTP guard (token, exact Host and Origin, preflight and form content-type rejection, no shell, fixed allowlist) and asked for two fixes before landing: bundle member validation against the live session list, and the strict live-pane validator for the write path. Both are done above, with a fixture test for each failure shape that asserts the tool never starts. It also asked for the page to stop falling back to the raw static snapshot (done: the page only reads the snapshot through the server, which refuses one that carries a private value) and for symlink checks on bundle components (done).

Kept as documented follow-ups:

- The manual session id is on the command line of the registry's `register` call for the life of that one process. It is never echoed or logged. Accepting it on stdin is companion task 2 below and is the next privacy hardening step.
- The listener change in `setup/serve.sh` makes every app that script serves loopback-only, which removes LAN access to the unrelated local apps. That is the intended protection for this cockpit, but confirm it is intended for the shared server before release.
- The reviewer could not complete a live visual check, so a second person should open the page and look at it before release. The author checked it in a browser at desktop and 390 px width.
- The raw snapshot file is still reachable through the shared static file handler, which sends a wildcard CORS header. The page no longer uses it. Closing that is outside this change.

## Share report

Built on the server, by construction, from an allowlist of fields: pane id, classification, candidate count, exact-match count, evidence categories, failure kind and counts, and the preflight summary.
Raw tool output is never passed through.
A second-layer leak scan then rejects the report if it finds UUID-like strings, `/Users/` paths, socket paths, `resume` command text or a bundle id; if it trips, no report is produced.
The report is markdown with a header listing what is excluded; the page offers copy and download and uploads nothing.
To hand it to someone: read it once, then paste it into Slack or a ticket. Session ids, resume commands, private paths and bundle ids never appear in any mode.
The leak scan and the masking are covered by tests that plant fake leaks.

## Sessions and the restart gap

Bundles are listed from the tool's own private folder (`bundles` action): only the id, time, bundled session names and readiness are returned, never the folders in a manifest. Whether the computer has restarted since a bundle was sealed comes from the bundle's seal time against the machine's boot time, so it survives the browser and the server restarting. A bundle whose reconcile journal already exists is a finished cycle: a fresh check on the page starts a new one.
`reconcile-preview` runs the tool's own read-only `reconcile-all --bundle ID` (never `--confirm`) once every bundled session is running, and returns adopt, rebuild and ambiguous counts per session plus the copy-only confirm, resume, rollback and extra-copy commands, built from the validated id.

Pane ids are unique only inside one session, so every action uses `session + pane`.
The browser's memory does not survive a restart, so the page derives the current step from real state:

| Fact | Step |
|---|---|
| Ready bundle exists and a bundled session is not running | Attach that session in a terminal |
| All bundled sessions running | Reconcile preview is available (the page runs it) |
| Preview clean | Copy the confirm command and run it in a terminal |

Source of truth is the system; the checklist is a projection of it. Only unprovable steps ("I restarted") stay informational.
The preflight is always called with an explicit `--session` list, because without it Herdr selects every running session.

## Clean up empty tabs in every workspace

`herdr-organizer cleanup-empty-tabs` only takes one `--workspace`, so the page does the fan-out.
`cleanup-preview {session}` lists the live workspace ids (pattern `^w[A-Za-z0-9]{1,10}$`, taken from the live pane list), runs the preview for each with at most four at a time, and aggregates the result: tabs to close per workspace, tabs the tool protects (agent, resumable session, non-shell process), and workspaces that close entirely. A workspace whose every tab is an empty shell closes with its last tab (`close_workspace` in the preview, `totals.workspaces_to_close` in the response). Two cases keep the last tab and carry a `kept_reason`: the workspace the command would run inside (`running_inside`) and the only workspace in the session (`only_workspace`). The page still only copies the closing command.
The response also carries two copy-only commands built from those validated ids: a loop that previews every workspace, and a `&&`-joined `--execute --confirm` chain for exactly the workspaces that have something to close.
The page never runs the execute form. The tool recomputes what is eligible when it runs, so a stale preview cannot close a protected tab.

## Archive all and restore a group

Decided 2026-10-07. The page gets an "Archive all workspaces" card (Workspaces tab) and a "Capture groups" area (Archives tab). Neither runs anything that closes or recreates a workspace.

- `archive-all` (in `workspace-organizer.py`, `personal` project) archives every live workspace that passes the same guards as `archive`, and stamps one `batch_id` (`batch-YYYYMMDD-HHMMSS`) on every archive it creates. A session has one such group for good (the `archive group`): a later `archive-all` adds to it, a member leaves it when its archive is restored or deleted, and older per-run groups are merged into the session's oldest one by the first locking group command. A workspace whose layout copy (a workspace a restore built, never just a reused id) is still an archived member replaces that member. A manifest in `state/workspace-organizer/batches/` lists the archived member ids and the skipped workspaces of the latest run with reasons (`active_agent`, `unverified_agent_session`, `capture_failed`, `workspace_gone`, `workspace_changed`). It never holds session ids or resume commands. Existing archives stay single cards; there is no timestamp clustering.
- The allow flags do not exist on `archive-all`, so nothing can pass them. Each workspace is re-assessed against a fresh snapshot right before it is closed, and one that changed is skipped. A failed close leaves its archive as `close_failed` and the run continues, then exits non-zero. Any other error or Ctrl-C closes out the record in a `finally` block: the group becomes `interrupted`. The archive being closed is labelled from the live workspace list, not guessed: workspace id gone from the list means `archived` (the interrupt landed after the close; the id alone decides, so a workspace renamed meanwhile is still treated as open), still listed or an unreadable list means `close_failed`. A hard kill (SIGKILL) cannot be handled and leaves `in_progress`.
- `archive-all --execute` stops before closing anything if it runs inside a workspace on its own list (`HERDR_PANE_ID` or `HERDR_WORKSPACE_ID` in the target session). The server strips those variables from child processes, so this guard only matters for the copied command, which is meant for a terminal outside Herdr. Confirmation is the session name.
- `archive-all-preview {session}` (tier 0) runs the tool's read-only `archive-all`. The `archive-all` command lives in the `personal` project, which this repo cannot push to its personal remote, so an older copy of the tool rejects the subcommand: the server turns that into a `tool_outdated` message (HTTP 501) that names the file to update, instead of a generic failure. Workspaces the parser drops (a malformed id) or that the tool counted but did not list are reported as `totals.omitted`, and the page warns that the list is incomplete. The parser keeps only fixed fields: ids must match their patterns, reasons are an allowlist, labels are scrubbed, and the tool's free-text `error` on a skipped row is dropped. The response carries the copy-only `archive-all --execute --confirm <session>` command, built from the validated session name and only when something would be archived. The page disables the copy button once the snapshot changes after the preview.
- `archive-all` skips an agent that is not in the registry, which is a different test from the identity check. A skipped pane therefore starts with a "Set session id" button, which opens the manual identity form at once, and a "Check identity" button (the Restart tab's own `verify` action, with elapsed time while it runs; it can take minutes). "Set session id" stays available while the check runs, so nothing waits for it, and the card keeps the typed text and caret across its once-a-second re-render. After a check, the result decides what the pane offers: a pane the check **verified** gets "Apply verified identities" (the existing `verify-apply` action and confirm), because a manual id can never overwrite a verified identity; an **ambiguous or unresolved** pane gets the Restart tab's manual identity form (same `save-manual-identity` action, confirm token and store checks); a pane the check did not list asks for a fresh check. After either, the user previews again. The apply result is kept per card and cleared by a new check, and it only says what the tool wrote for the session ("applied, preview again"). The page never labels a pane "registered" from a session-wide count, and ignores an apply result from the Restart tab.
- A layout-only restore never counts as a restore. `restore` and `restore-batch` without `--resume-agents` rebuild the layout, leave the archive `archived` with all its restore commands, and record the open workspace in `layout_restore`. Only a restore with `--resume-agents` marks an archive `restored` or `resumed`. When the recorded layout copy is still listed by Herdr and is exactly what the restore built (the same tabs, the capture's layout shape and the pane ids the restore recorded in `layout_restore`), `--resume-agents` resumes the agents inside it (the tool re-reads the live layout to rebuild the pane map and never types into a pane that already shows an agent) instead of making a new workspace. A closed, rebuilt, rearranged, partly replaced or half-built copy is never adopted. A copy from an interrupted restore has no recorded pane ids and is not reused, and a record made before pane ids were kept adopts on the layout shape alone. An interrupted layout-only restore leaves the archive `archived`; an interrupted restore with resume leaves `restore_partial`, and running the command again retries it. The group card shows such members as "layout open", keeps both restore buttons, and disables "Copy restore all (layout only)" only when every archived member already has its layout open.
- `restore-batch [--batch ID] [--resume-agents] --execute --confirm ID` (`--batch` defaults to the group of `--session`; restoring a member takes it out of the group) acts only on members whose archive status is `archived`; with `--resume-agents` each is resumed in its open layout copy or in a new workspace, without it each member without an open copy gets a layout. `restore_partial` and not-closed members are reported and left alone; restored and deleted ones are no longer in the group. It never uses `--force` or `--allow-unresumable-agents`, refuses a session other than the one the batch was captured from, re-reads each member's status inside the lock, and continues after a failure before exiting non-zero. `archive-all`, `restore-batch`, `delete-batch --archives` and the executing forms of the single `archive`, `restore`, `delete-archive`, `archive-tabs`, `restore-tab`, `restore-tabs`, `delete-archived-tab`, `move-tabs`, `resume-move`, `add-tabs-to-batch`, `finish-tab-add` and `cleanup-empty-tabs` share one non-blocking lock (`state/workspace-organizer/batch-run.lock`), so a second run is refused instead of duplicating work or overwriting an archive file another run is rewriting. This includes the per-workspace restore button on a group card, which copies the single `restore` command. **Not locked:** every preview (they change nothing), `snapshot`, `list-archives`, `list-batches`, `reorder-tab` (it only reorders tabs in a live workspace and touches no archive), `delete-batch` without `--archives` (it removes only the group record), and the restart-recovery commands (`prepare-restart-recovery`, `reconcile-all`, `rollback-reconcile`), which have their own per-bundle locks.
- The snapshot carries `batches`: counts per status, members with live status read from each archive file (a missing file is `deleted`), and skipped rows (fixed fields only). The group lives on its own Archive group tab, and the Archives tab lists only individual archives (a chip marks those currently in the group). The group card offers two copy-only buttons, "Copy restore all + resume agents" (primary) and "Copy restore all (layout only)", disabled when no member is still archived. Each member that is still `archived` also has its own copy-only "Copy restore + resume agents" (the single-archive `restore --archive ID --resume-agents`, with the group's session), so one workspace can be restored without the rest. Every group has a delete: "Copy delete group + N archives" (`delete-batch --archives`, which needs its own confirm value `delete-archives:<batch id>` so the record-only confirm cannot authorize it, and which permanently deletes the group record and every member archive whose own `batch_id` matches, keeps the record if any archive cannot be deleted, and says when members are still archived because their saved layouts and agent identities would be lost; the page shows that warning as visible text on the card, not only a tooltip) and "Copy delete group record only" (the archives stay as single archives). An empty group, where every archive is already gone, shows a single "Copy delete group". All are copy-only; live and restored workspaces are never touched.

## Add selected tabs to a restore group

Decided 2026-10-12 (adaptive review, then built directly in the working trees). The selected-tabs panel on the Workspaces view has three modes: Move, Archive, and "Add to restore group". The last one is copy-only like the others.

- The page offers only the finished group (`completed` or `completed_with_failures`) of the session the snapshot came from, and copies two commands built from validated ids and the group's own session: a read-only preview (`add-tabs-to-batch --batch ID --tab T ...`) and the execute form (`--execute --confirm ID`). With no group at all for the session the panel offers to start one (`add-tabs-to-batch` without `--batch`, executed with `--confirm <session>`); only a group whose last run did not finish disables the button, and the panel says to run Archive all again. No new server action exists: the page already has `batches` in the snapshot, and the executing command is never run by the page.
- `add-tabs-to-batch` captures the selected tabs, then closes them and stops their processes. It refuses working or blocked agents and agents without a verified resumable session, with no override flag, refuses a session other than the group's, and takes the shared run lock when it executes.
- `add-tabs-to-batch` matches a live workspace to an existing member by the member's original workspace id only while that workspace can still be open: the member is a selected-tabs archive that never closed its workspace (`origin_workspace_still_open`). Herdr hands a closed workspace's id and tab ids out again, so a whole-workspace archive, or one whose workspace was closed by an earlier add, never matches by id (found 2026-10-20: a new `BC-36` workspace reusing `wBM` was refused with "already contains tab(s)" and would otherwise have merged into the closed `misc-task` archive). A workspace a restore built still matches through the archive's restore record.
- Tabs from one live workspace become one new batch member labelled `<workspace> (selected tabs)`. If that workspace is already tied to a still-archived member of the group (for example through its open layout copy), the tabs merge into the member instead. A restored workspace is no longer in the group, so its tabs become a new member. The match uses exact recorded workspace ids only (the member's restored workspace, its open layout workspace, or its original workspace), never the label, and two matching members stop the run.
- A merged member goes back to `archived`. Its old `restore` and `layout_restore` records move to `restore_history`, so adoption never reuses them. A selected tab that an earlier restore rebuilt replaces its captured original in place, using the `source_tab_id` to `tab_id` pairs in those records. Other selected tabs are appended.
- Selecting every tab of a workspace archives it whole and closes the workspace. The workspace the command runs inside, and the only workspace in the session, keep one tab open. A partial selection that includes the tab the command runs in is refused.
- Right before anything closes, the command reads the live session again. A selected tab that gained a pane, a working agent or a different layout, or a workspace about to close that gained a tab, stops the run with nothing closed and the whole addition undone (the new archive and manifest entry are removed, a merged member is written back as it was). `cleanup-empty-tabs` does the same before its own closes. A tab that already closed by itself is skipped.
- While the tabs close, the archive is `prepared`, so a group restore leaves it alone. Each tab's close is recorded in the operation. A failed or interrupted close is settled from the live tab list: every captured tab gone means `archived`, otherwise `close_failed` with the still-open tab ids and an operation marked `close_partial`. That archive is outside `restore` and `restore-batch` until `finish-tab-add --archive ID` (copy-only from the page's point of view, run by the user) checks the still-open tabs again, refuses if they changed, closes only the ones still open and makes the archive `archived`.

**Known risk (accepted by the user).** Captured tabs of a restored member that are not part of the selection stay in the archive. The next restore rebuilds them even if they are still open in the earlier restored workspace, and agents already resumed there resume again. The preview warns only in that case. When every captured tab is replaced by its rebuilt copy, nothing is duplicated. The alternative, not chosen, is to record which tabs are already restored and rebuild only the new ones; revisit it if duplicates appear in real use.

## Architecture

All new code is isolated under `setup/herdr-organizer/` so `serve.sh` stays a thin shell (its Node program lives in a bash string, which is hard to test).

- `api.js` - request guard and dispatcher; `serve.sh` requires it and delegates `/api/herdr-organizer/*` before the CORS handler.
- `adapter.js` - the only place that spawns Herdr tooling. Fixed argument builders, and parsers for the verifier and preflight text output. The runner is injectable so tests use fixtures.
- `guard.js` - Host, Origin, Fetch-Metadata and token checks.
- `redact.js` - share report builder and leak scan.
- `store_check.py` - read-only store and folder check for manual identity (imports the verifier's store classes).
- `test/` - `node --test` tests with fixtures.

The tool root defaults to `personal/01-System/setup/herdr` and can be overridden with `HERDR_ORGANIZER_TOOL_ROOT`, so tests and local runs can use a scratch copy and never write into a real registry or bundle directory.
`HERDR_LAB_HELPER`, when set, is passed through to the organizer (it already routes Herdr calls through the isolated lab).

## Out of scope for v1

- Running `reconcile --confirm`, rollback, archive, restore or tab moves from the page.
- `/status` capture (sends input into panes), resume replay, Herdr integration install, auto-recovery at login.
- Candidate picker for manual identity (masked ids plus last-activity time), remote or multi-machine access.

## Companion tasks for `personal` (firstmate to dispatch)

The page is built against the interface as it exists today, through the adapter. These would remove parsing and exposure risk:

1. JSON output mode for `herdr-agent-verify-identity` and for the `prepare-restart-recovery` preflight (stable fields instead of text parsing).
2. `register` accepting the session id on stdin so it never appears in `ps`.
3. A check-id option on the verifier (exists in store, folder matches, already registered) so the page does not import store classes.
4. A `state-root` override environment variable for the organizer and registry, so isolated runs do not need a scratch copy of the scripts.
5. Verifier speed, the biggest practical problem found. `ClaudeStore.records()` and `CodexStore.records()` re-walk and re-read every session file on each call, and `verify_pane` calls them up to three times per pane (`agent_identity_verifier.py` lines 341, 372, 390, 415, 450 and 480). With 24 panes and about 540 Claude session files that is roughly 40 s of CPU, and several minutes of wall time on a busy machine. Memoizing the record list for the life of one run (a per-run cache passed through `stores`) would make it about one pass instead of one per pane per lookup. Related: `cleanup-empty-tabs --all-workspaces` (one snapshot instead of one process per workspace) and progress output for the verifier.
6. Optional: a list-candidates command that returns masked ids and last-activity times, for a later candidate picker.

## Findings from real runs

- The identity verifier is slow on a busy machine: about 40 s of CPU, and several minutes of wall time with a load average near 30. The server allows 15 minutes for the verifier (10 for the preflight), shares one run between identical in-flight requests (a page reload or second tab does not start another), and the page does not auto-run it on load. It shows the elapsed time while it waits. A run that is stopped for taking too long is reported as a timeout (HTTP 504) rather than as a broken tool; on this machine the first real checks hit that limit while the load average was above 100 (confirmed through the API: a real identity check was stopped at 913 s with the timeout message, and the real registry files were untouched).
- The preflight reads the registry manifest next to the tool scripts. A scratch copy of the scripts without that manifest reports every agent as unverified, so isolated copies are for writes only; read-only checks against a real session use the real tool root.
- A stopped Herdr session on this machine is literally named `-h`; session names are therefore never allowed to start with a dash.

## Leader space convention (2026-10-19)

Every firstmate and secondmate session lives in one Herdr workspace named `leader-space`, one tab each: `big-boss` (firstmate) and `leader-esim`, `leader-workspaceos`, `leader-nip`, `leader-fleet-watch`, `leader-personal-work`. A label is an identity and exists at most once. Crewmates and scouts stay out of it, each in the workspace of its own task.
Why: a restore with agent resume plus the watcher's secondmate liveness tick duplicated panes, because the tick relaunches from the recorded endpoint and never looks for a live agent elsewhere.

- Labels sit on both the tab (`herdr tab rename`) and the pane (`herdr pane rename`). Only the pane label shows in `herdr pane list`, so a worker finds an identity by matching `label` there.
